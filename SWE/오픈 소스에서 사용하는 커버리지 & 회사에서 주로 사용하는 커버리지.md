# 오픈 소스에서 사용하는 커버리지
- 오픈 소스 프로젝트 커버리지의 특징
	- 기여자가 불특정 다수 => 커버리지 측정과 리포팅이 **CI에 자동화**되어 있고 결과가 **공개**됨 (README 배지, PR 코멘트)
	- 측정 기준은 대부분 **구문(라인) 커버리지 + 분기 커버리지** 수준까지만 사용 (MC/DC 같은 고비용 기준은 거의 사용하지 않음)
	- 전체 커버리지 수치보다 **PR에서 바뀐 줄이 테스트되었는가(패치 커버리지, diff coverage)** 를 중요하게 봄
	- 도구는 언어 표준 도구(무료) + 공개 저장소에 무료인 SaaS 리포팅 서비스(Codecov, Coveralls) 조합이 일반적

## 언어별로 주로 쓰는 측정 도구

| 언어      | 측정 도구                                 | 측정 단위              | 비고                                           |
| ------- | ------------------------------------- | ------------------ | -------------------------------------------- |
| Java    | JaCoCo                                | 명령어·라인·분기·메서드·클래스  | Maven/Gradle 플러그인, XML 리포트를 SonarQube·Codecov가 읽음 |
| Python  | coverage.py (+ pytest-cov)            | 라인·분기              | `.coveragerc`로 제외 경로 지정                       |
| JS/TS   | Istanbul(nyc), c8 (V8 내장 커버리지)         | 라인·분기·함수·구문        | c8은 `check-coverage --lines 95 --branches 95` 식으로 임계값 검사 |
| Go      | `go test -cover` (내장)                   | 구문(statement)      | `-covermode=atomic`, `go tool covdata merge`로 병합 |
| C/C++   | gcov + lcov, llvm-cov                  | 라인·분기·함수           | Linux 커널은 gcov 외에 퍼징용 KCOV 사용                  |

## 오픈 소스용 커버리지 리포팅 서비스

| 항목        | Codecov                                            | Coveralls                       |
| --------- | -------------------------------------------------- | ------------------------------- |
| 공개 저장소 요금 | 무료 (무제한)                                            | 무료                              |
| 비공개 저장소   | Developer 무료(월 250 업로드 제한) → Team $5/인/월 → Pro $12/인/월 | 유료 플랜 (5인 $29/월 수준)             |
| 기본 판정 기준  | project: `target: auto`, `threshold: 5%` / patch: `target: auto`, `threshold: 0%` | 기존 대비 하락 여부                     |
| 설정 파일     | `codecov.yml`                                        | `.coveralls.yml`                |
| 특징        | 도구·언어 무관, PR에 patch/project 두 가지 상태 체크 표시            | 오래된 서비스, 시간 경과에 따른 추세 그래프        |

- `target: auto` = 기준 브랜치(base) 커버리지를 목표로 삼음 => "떨어뜨리지만 마라"
- `patch` = PR에서 추가·수정된 줄만 계산한 커버리지 => 전체가 90%여도 새로 넣은 10줄 중 5줄만 테스트되면 patch 50%

## 실제 오픈 소스 프로젝트 사례

| 프로젝트                | 언어       | 측정 도구                 | 리포팅/게이트                                     | 실제 기준·수치                                                                                                     |
| ------------------- | -------- | --------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| pytest              | Python   | coverage.py           | Codecov                                     | `codecov.yml`: **patch target 100%**, project 체크는 `false`, PR 코멘트 끔 => "새 코드는 전부 테스트, 전체 수치는 강제 안 함"         |
| Apache Commons Lang | Java     | JaCoCo (Maven)        | 빌드 자체가 게이트 (`haltOnFailure=true`)           | `pom.xml` 최소 비율: class 0.98 / instruction 0.96 / method 0.96 / line 0.96 / **branch 0.92** / complexity 0.91 |
| Node.js (core)      | JS + C++ | c8(V8 내장), gcov/lcov  | coverage.nodejs.org → 현재 Codecov로 리다이렉트     | 커뮤니티 회고 기준 JS 89.4% → 94.3%, C++ 88.3% → 91.4%까지 개선. 나이틀리로 측정·공개                                             |
| Django              | Python   | coverage.py           | CI가 **diff-cover**로 PR 변경 줄만 리포트            | 공식 정책: "누락된 커버리지는 **차단(blocker)이 아닌 경고(warning)**로 보고 맥락에 따라 판단". DB·OS별 코드는 미커버 허용                          |
| Kubernetes          | Go       | `go test` + gopherage | TestGrid(sig-testing-canaries), 선택적 Codecov | `KUBE_COVER=y`로 unit·conformance·e2e 커버리지를 **매 1시간** 주기 잡으로 수집, 생성 코드(deepcopy·clientset 등) 제외. PR 잡은 수동 트리거 |
| Linux 커널            | C        | gcov, KCOV            | 없음 (개발자·퍼저 로컬 사용)                           | 커버리지 %를 관리하지 않음. KCOV는 syzkaller 퍼징 피드백용(2개월 만에 커널 버그 90개 발견)                                                |
| CPython             | C/Python | coverage.py           | 개발자 가이드에 측정 방법만 안내                          | `./python -m test --coverage`, 강제 기준 없음                                                                      |

## 오픈 소스 커버리지 실태 연구
- Hilton, Bell, Marinov, *A Large-Scale Study of Test Coverage Evolution* (ASE 2018)
	- 오픈 소스 47개 프로젝트, 7,816개 빌드를 Coveralls 데이터와 직접 실행으로 분석
	- 발견 1: **패치 커버리지와 전체 커버리지는 상관관계가 없음** => 전체 90%인 프로젝트도 특정 PR은 0%일 수 있음
	- 발견 2: 개별 패치가 전체 커버리지를 크게 흔들 수 있음
	- Java 프로젝트 29개 중 60% 미만은 6개, 20% 미만은 1개 => 대부분 60% 이상 유지
- 시사점: 오픈 소스가 patch coverage 게이트를 선호하는 이유가 여기서 나옴 (전체 수치는 후행 지표)


# 회사에서 주로 사용하는 커버리지
- 회사(기업) 커버리지의 특징
	- 목적이 "공개 신뢰"가 아니라 **배포 게이트·품질 게이트·감사(audit) 증빙**
	- 커버리지 도구를 단독으로 쓰기보다 **정적 분석 플랫폼(SonarQube 등)에 커버리지를 넣어 Quality Gate로 묶음**
	- "전체 커버리지 X% 이상" + "**신규 코드 커버리지** Y% 이상" 두 축을 같이 봄
	- 도메인이 안전-필수(항공·자동차·의료)면 라인/분기가 아니라 **MC/DC**까지 요구되고, 도구도 인증된 상용 제품 사용

## 회사에서 주로 쓰는 도구

| 분류          | 도구                                           | 특징                                                              |
| ----------- | -------------------------------------------- | --------------------------------------------------------------- |
| 품질 플랫폼      | SonarQube (Server / Cloud / Community)       | 커버리지를 직접 측정하지 않고 JaCoCo·coverage.py·lcov 리포트를 읽어 Quality Gate 판정 |
| Java        | JaCoCo, OpenClover (구 Atlassian Clover)      | Clover는 2017-04-11 판매 종료 후 OpenClover로 오픈 소스화                    |
| .NET        | Coverlet, Visual Studio Enterprise 코드 커버리지, JetBrains dotCover | VS Enterprise·dotCover는 유료                                       |
| C/C++ 안전-필수 | VectorCAST, LDRA, Parasoft C/C++test, Bullseye | DO-178C·ISO 26262 인증 키트 제공, MC/DC 측정 지원                           |
| 사내 자체 구축    | Google 내부 커버리지 인프라 + Critique(코드 리뷰 도구)        | 하루 10억 줄, 7개 언어, 라인 커버리지를 리뷰 화면에 색으로 표시                          |

## 회사 사례

| 회사 / 기준                   | 사용 도구                                        | 측정 기준             | 임계값·정책                                                                                                     | 미달 시 조치                             |
| ------------------------- | -------------------------------------------- | ----------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| Google                    | 자체 인프라 + Critique                            | **라인 커버리지**       | 가이드라인 **60% acceptable / 75% commendable / 90% exemplary**. 팀별 자율, 전사 강제 없음. 리뷰 시 변경분(changelist) 커버리지 표시   | 차단 없음 (2018년 1분기 기준 프로젝트 90% 이상이 자발 사용) |
| SonarQube 기본 게이트 (Sonar way) | SonarQube                                    | 신규 코드 라인+조건 커버리지  | **신규 코드 커버리지 ≥ 80%**, 중복 ≤ 3%, 신뢰성·유지보수성·보안 등급 A, 보안 핫스팟 검토 100%                                             | Quality Gate 실패 → PR 머지·배포 차단        |
| 우아한형제들 (2020 기술블로그)        | JaCoCo (Gradle `jacocoTestCoverageVerification`) | 클래스 단위 라인·분기      | 예시 설정: 클래스별 **라인 80% / 분기 90%**, 클래스당 200줄 초과 금지. QueryDSL `Q*` 등 생성 코드 제외. 기준을 조금씩 올려 가며 분기 100% 프로젝트도 있음 | 빌드 실패 → 배포 불가                       |
| 토스 (SLASH 21, 2021)         | JaCoCo (Gradle `jacocoTestCoverageVerification`) | 라인·분기             | Kotlin+Spring 서버를 **100%** 로 올리고 1년 6개월 유지. "90·95%보다 100%가 오히려 단순한 기준". Kotlin 바이트코드(엘비스 연산자 등) 때문에 코드 스타일 조정 | 기준 미달 시 배포 차단                       |
| 카카오페이                     | SonarQube (샌드박스 환경) + GitHub PR 연동             | Quality Gate 등급    | PR마다 자동 분석 후 결과를 GitHub에 리포트. 등급 C면 게이트 실패, A로 개선 후 통과 (수치 자체는 비공개)                                          | Quality Gate 실패 → 머지 차단              |
| 항공 (DO-178C)              | VectorCAST, LDRA 등 인증 도구                     | 구문·결정·**MC/DC**   | Table A-7: Level A = MC/DC, Level B = 결정(decision), Level C = 구문(statement), Level D = 요구 없음                | 인증 심사 불통과 (출하 불가)                   |
| 자동차 (ISO 26262-6)         | 동일                                           | 구문·분기·MC/DC       | Table 9: 아래 표 참고                                                                                            | ASIL 심사 불통과                         |

### ISO 26262-6 Table 9 (단위 수준 구조적 커버리지)

| 방법           | ASIL A | ASIL B | ASIL C | ASIL D |
| ------------ | ------ | ------ | ------ | ------ |
| 1a 구문 커버리지    | ++     | ++     | +      | +      |
| 1b 분기 커버리지    | +      | ++     | ++     | ++     |
| 1c MC/DC     | +      | +      | +      | ++     |

- `++` = 강력 권장(highly recommended), `+` = 권장(recommended)
- ASIL이 올라갈수록 요구 기준이 구문 → 분기 → MC/DC로 강해짐

## Google 사례 상세 (Code Coverage at Google, ESEC/FSE 2019)
- 규모: 하루 **10억 줄**, 7개 언어, 하루 수만 건 커밋에 대해 커버리지 계산
- 표시 방식: 코드 리뷰 도구 Critique에서 줄 번호를 초록(커버)/주황(미커버)/흰색(미계측)으로 색칠, 전체 커버리지 + 변경분 커버리지를 함께 표시
- 강제 아님: 옵트인 방식인데도 2018년 1분기 기준 프로젝트의 90% 이상이 사용
- 설문(3,000명 중 512명 응답): 45%가 코드 작성 시, 40%가 리뷰 시 커버리지를 자주 활용
- 결론: 커버리지 증가의 효용은 **로그 함수적** => 30%→70%는 노력할 가치가 있으나 그 이상은 체감이 작음. "품질 신호가 아니더라도(사용 안 하는 의존성 탐지 등) 계산할 가치가 있다"


# 오픈 소스와 회사의 차이 비교

| 비교 항목      | 오픈 소스                                                   | 회사                                                                 |
| ---------- | ------------------------------------------------------- | ------------------------------------------------------------------ |
| 목적         | 기여자·사용자에게 **공개 신뢰**, PR 리뷰 보조                            | **배포 게이트**, 품질 관리, 인증·감사 증빙                                        |
| 주 측정 기준    | 라인·분기 커버리지                                              | 라인·분기 + (안전-필수는) **MC/DC**                                         |
| 임계값 방식     | **패치 커버리지** 중심 (pytest patch 100%, Django diff-cover) / 전체 수치는 `auto`(하락 금지) | **절대값** 중심 (Sonar way 신규 80%, 우아한형제들 클래스 80/90%, 토스 100%) + 신규 코드 별도 |
| 강제 수준      | 경고~머지 차단 프로젝트마다 다름. Django는 명시적으로 "경고일 뿐"                | 대부분 **빌드 실패·배포 차단**. 안전-필수는 법적·인증 요구                               |
| 도구         | 언어 표준 무료 도구 + Codecov/Coveralls (공개 저장소 무료)             | SonarQube·JaCoCo 조합, .NET·C++는 상용 도구, 대기업은 자체 인프라(Google)          |
| 비용         | 거의 0원                                                   | SaaS 인당 과금, 상용 안전-필수 도구는 고가 라이선스                                   |
| 결과 공개      | 배지·대시보드 공개                                              | 사내 대시보드, 외부 비공개 (카카오페이처럼 수치 비공개)                                   |
| 제외 규칙      | 벤더 코드·생성 코드·플랫폼별 코드 (Kubernetes deepcopy, Django DB별 코드) | 생성 코드·DTO·설정 클래스 (우아한형제들 `Q*`), 단 안전-필수는 제외 자체를 정당화해야 함           |
| 커버리지 개선 방식 | 기여자에게 PR 단위로 요청                                         | 기준을 **점진적으로 상향**(ratchet)하거나 처음부터 높게 고정                            |
| 대표 수치      | 오픈 소스 Java 프로젝트 대다수 60% 이상 (Hilton 2018)                | Google 가이드 60/75/90%, SonarQube 신규 80%, 안전-필수 100% MC/DC            |

- 정리
	- 오픈 소스는 "**바뀐 코드가 테스트되었는가**"를 보고, 회사는 "**전체와 신규 코드가 기준 이상인가**"를 본다
	- 오픈 소스는 커버리지를 **리뷰 정보**로 쓰고, 회사는 **게이트(차단 장치)** 로 쓴다
	- 오픈 소스는 라인·분기에서 멈추지만, 회사는 도메인에 따라 MC/DC까지 올라간다 (항공 Level A, 자동차 ASIL D)
	- 둘 다 공통으로 인정하는 것: 100% 자체가 품질을 보장하지 않으며(Google, Django 문서 모두 명시), 생성 코드·플랫폼별 코드는 제외하고 측정한다
	- 회사라도 Google처럼 강제 없이 리뷰 정보로만 쓰는 곳이 있고, 토스처럼 100%를 강제하는 곳이 있어 "회사 = 엄격"이 절대적이지는 않음. 차이를 만드는 건 조직 형태보다 **배포 책임과 규제 여부**
