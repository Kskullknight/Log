# 컨테이너 오케스트레이션: 다수의 컨테이너를 자동으로 관리하고 운영한다.
## 컨테이너 오케스트레이션이란
- 다수의 컨테이너를 자동으로 관리하고 운영하는 것
- 로드 밸런싱, 헬스 체크, 스케일링이 핵심 기능

## 로드 밸런싱
- 들어오는 요청을 여러 컨테이너에 나누어 할당하여 부하를 분산하는 것
- 같은 역할의 컨테이너를 여러 개 띄우고 요청을 나누어 전달
- 한 컨테이너에 부하가 몰리는 것을 막아 응답 속도를 유지
- 일부 컨테이너가 멈춰도 나머지가 처리하여 서비스가 지속됨

## 헬스 체크
- 컨테이너가 정상적으로 동작 중인지 확인하는 것
- 컨테이너에 요청을 보내 정상 응답을 반환하는지 확인
- 이상이 발견된 컨테이너는 로드 밸런서가 요청 대상에서 제외

## 스케일링
- 부하에 맞춰 컨테이너의 수나 성능을 조절하는 것
- 요청이 많을 때는 늘리고 한가할 때는 줄여 리소스 소비를 최적화
- 리소스 부족으로 시스템이 다운되는 상황을 방지

## 오케스트레이션의 중요성
- 관리·운영하는 컨테이너 수가 늘수록 사람이 대응하기 어려워짐
- 장애 대응, 확장, 배포를 자동화하여 가용성과 운영 효율을 모두 확보

# 쿠버네티스: 컨테이너의 관리와 운영을 자동화하는 오케스트레이션 도구
## 쿠버네티스에서 가능한 것

| 기능                | 내용                                |
| ----------------- | --------------------------------- |
| 헬스 체크와 자동 복구      | 멈춘 컨테이너를 재기동                      |
| 스케일링              | 부하에 따라 컨테이너 수를 늘리고 줄임              |
| 엔드포인트 제공과 로드 밸런싱  | 고정된 IP로 접속하고 요청을 분산               |
| 롤링 업데이트·롤백        | 서비스를 멈추지 않고 새 버전으로 교체, 문제가 생기면 되돌림 |

## 쿠버네티스에서 불가능한 것
- 쿠버네티스는 컨테이너를 운영하는 도구일 뿐, 애플리케이션 개발의 모든 것을 해주지는 않음
- 자동 빌드: 별도의 CI/CD 도구가 필요
- 미들웨어: 직접 컨테이너로 올려야 함
- 로그 수집·모니터링: 기본으로 제공하지 않으며 외부 도구와 연동
- 서버 자체의 구축·유지 보수: 인프라는 따로 준비해야 함

## 컨테이너 오케스트레이션 도구의 사실상 표준
- 도커 스웜, 아파치 메소스 등과 경쟁했으나 쿠버네티스가 사실상 표준이 됨
- AWS(EKS), GCP(GKE), Azure(AKS) 등 주요 클라우드가 모두 관리형 쿠버네티스를 제공

## 쿠버네티스 클러스터란
- 클러스터: 쿠버네티스가 관리하는 서버와 컨테이너의 집합
- 노드: 클러스터를 구성하는 서버 한 대

### 노드의 두 가지 유형

| 구분  | 마스터 노드  | 워커 노드      |
| --- | ------- | ---------- |
| 역할  | 워커를 제어  | 파드를 실제로 실행 |

# 파드: 쿠버네티스가 컨테이너를 관리하는 최소 단위
## 파드란
- 파드(Pod): 쿠버네티스가 컨테이너를 관리하는 최소 단위
	- 하나 이상의 컨테이너로 구성

| 파드 내 컨테이너가 공유하는 것 | 내용                                    |
| ----------------- | ------------------------------------- |
| 네트워크              | 파드마다 IP 주소가 하나, 내부 컨테이너끼리는 localhost로 통신 |
| 스토리지              | 파드에 정의한 볼륨을 여러 컨테이너가 함께 마운트           |
| 생명 주기             | 같은 노드에 함께 배치되고 함께 생성·삭제               |

> [!note]+ 마운트(mount)
>
> - 저장 장치나 볼륨을 디렉터리 트리의 특정 경로에 연결하여 그 경로로 접근할 수 있게 하는 것
> - 볼륨을 컨테이너의 `/data`에 마운트하면, 컨테이너가 `/data`에 쓴 파일은 볼륨에 저장됨
> - 여러 컨테이너가 같은 볼륨을 마운트하면 파일을 공유할 수 있음

## 파드의 필요성
- 파드 안에서 여러 컨테이너를 시작하면 쿠버네티스가 그 컨테이너들을 하나의 단위로 관리할 수 있음

## 파드의 디자인 패턴
- 일반적으로 파드당 컨테이너는 하나
- 사이드카 컨테이너: 메인 컨테이너에 추가하여 보조 역할을 맡는 컨테이너
	- 메인 컨테이너를 고치지 않고 기능을 보완

| 사용 예  | 내용                                 |
| ----- | ---------------------------------- |
| 로그 수집 | 메인 컨테이너가 파일로 남긴 로그를 사이드카가 읽어 외부로 전송 |
| 프록시   | 통신을 가로채 암호화, 재시도, 감시를 수행           |

# 디플로이먼트 컨트롤러: 파드를 원하는 상태로 유지한다.
## 레플리카셋이란
- 레플리카셋(ReplicaSet): 똑같은 파드를 지정한 개수만큼 복제하여 유지하는 기능
- 하나 이상의 파드 그룹
- 같은 유형의 파드만 포함
- 헬스 체크와 스케일링을 수행

## 디플로이먼트란
- 디플로이먼트(Deployment): 레플리카셋을 관리하는 기능
- 하나 이상의 레플리카셋 그룹
- 레플리카셋이 유지하는 파드 수를 바꾸거나 새 레플리카셋을 만듦
- 디플로이먼트 => (관리) => 레플리카셋 => (관리) => 파드

| 기능      | 내용                                   |
| ------- | ------------------------------------ |
| 롤링 업데이트 | 새 레플리카셋을 만들고 파드를 조금씩 새 버전으로 교체       |
| 롤백      | 이전 레플리카셋을 남겨 두어 문제가 생기면 이전 버전으로 되돌림  |
| 스케일링    | replicas 값을 바꿔 파드 수를 조절             |

## 컨트롤러란
- 객체의 현재 상태를 감시하며 원하는 상태와 같아지도록 조정하는 것

## 디플로이먼트 컨트롤러란
- 디플로이먼트를 특정 상태로 유지하는 컨트롤러
- 마스터 노드의 kube-controller-manager 안에서 동작
- 컨테이너에 변경이 있는 경우 새 파드를 실행하고 기존 파드를 정지

# 서비스: 컨테이너에 접속하는 창구인 엔드포인트를 제공한다.
## 서비스란
- 서비스(Service): 컨테이너에 접속하기 위한 창구인 엔드포인트를 제공하는 방식
- 외부에서는 컨테이너에 직접 접속하지 않고 엔드포인트를 통해 간접적으로 접속

| 구분    | 컨테이너에 접속하는 방법                                      |
| ----- | -------------------------------------------------- |
| 도커    | 컨테이너 실행 시 컴퓨터 포트와 컨테이너 포트를 바인딩(할당)하고, 바인딩된 컴퓨터 포트로 접속 |
| 쿠버네티스 | 엔드포인트(서비스)에 접속하면 대상 컨테이너로 전환                       |

- 쿠버네티스에서는 레플리카셋과 디플로이먼트 구조 때문에 컨테이너(정확히는 파드)가 실행과 정지를 반복함
- 접속 대상 컨테이너가 같은 시스템에서 실행된다고 단정할 수 없음
- 이런 상황에서도 대상 컨테이너에 정확히 접속하게 해주는 방법이 서비스
- 다른 프로세스 => (접속) => 엔드포인트 => (전환) => 파드(컨테이너)

## 서비스의 구조
- 가상 IP 주소와 네트워크 주소 변환을 조합하여 동작

| 용어         | 내용                                      |
| ---------- | --------------------------------------- |
| 가상 IP 주소   | 물리적 또는 가상 컴퓨터에 할당할 수 없는 IP 주소, 엔드포인트 역할 |
| 네트워크 주소 변환 | IP 주소를 다른 IP 주소로 바꾸는 기술                 |

- 가상 IP(엔드포인트)에 접속하면 네트워크 주소 변환에 따라 대상 컨테이너로 전달됨

### 접속 전환 예시
1. 엔드포인트의 가상 IP `10.240.0.100`에 접속
2. 서비스의 작동 방식에 따라 네트워크 주소가 변환됨
3. 파드 A의 가상 IP `10.240.0.101`로 접속이 전환됨

- 네트워크 주소 변환 결과에 따라 파드 B(`10.240.0.102`)나 파드 C(`10.240.0.103`)로 전환될 수도 있음

## 서비스 유형
- 엔드포인트를 제공하는 방법에 따라 네 가지 유형으로 나뉨

| 서비스 유형       | 특징                                            |
| ------------ | --------------------------------------------- |
| ClusterIP    | 클러스터 내부에서만 접속할 수 있는 가상 IP 주소가 생성됨             |
| NodePort     | 클러스터의 모든 노드의 지정된 포트로 접속한 것이 컨테이너로 전달됨, 외부에서도 접속 가능 |
| LoadBalancer | 클라우드 서비스의 로드 밸런서로 접속한 것이 컨테이너로 전송됨, 외부에서도 접속 가능 |
| ExternalName | 서비스에 대한 접속이 지정된 호스트로 전달됨                      |

### 각 서비스의 구분

| 상황                              | 적합한 유형       |
| ------------------------------- | ------------ |
| 웹 서버 => DB처럼 클러스터 내부끼리 통신       | ClusterIP    |
| 개발·테스트 중 간단히 외부에서 접속            | NodePort     |
| 클라우드에서 운영 서비스를 외부에 공개           | LoadBalancer |
| 클러스터 안에서 외부 DB·API를 서비스 이름으로 참조 | ExternalName |

- LoadBalancer는 서비스마다 로드 밸런서가 생겨 비용이 발생
	- 서비스가 많으면 인그레스(Ingress) 하나로 묶어서 공개

## 서비스에 의한 로드 밸런싱

| 서비스의 역할  | 내용                                              |
| -------- | ----------------------------------------------- |
| 엔드포인트 제공 | 컨테이너에 접속하기 위한 창구                                |
| 로드 밸런싱   | 엔드포인트 접속을 여러 컴퓨터에서 실행되는 같은 유형의 컨테이너로 분배, 서버당 부하를 줄임 |

- 쿠버네티스의 서비스는 `Discovery & LB` 리소스 유형으로 분류됨
	- 이름 확인(discovery)과 로드 밸런싱, 두 문제를 해결
- ExternalName을 제외한 서비스는 쿠버네티스가 자동으로 로드 밸런싱을 수행
- ExternalName은 대상 호스트가 로드 밸런싱을 하도록 사용자가 직접 구성해야 함

# 플라넬: 서로 다른 노드에 있는 파드끼리 통신하게 해주는 오버레이 네트워크
## 파드 내 통신
- 같은 파드의 컨테이너들은 네트워크 네임스페이스를 공유
- 서로 `localhost:포트번호`로 통신
- 같은 파드 안에서는 포트 번호가 겹치면 안 됨

## 파드 간 통신
- 모든 파드에는 고유한 IP 주소가 할당되어, 서로의 IP 주소로 직접 통신할 수 있어야 함

| 경우          | 통신 방법                |
| ----------- | -------------------- |
| 같은 노드의 파드끼리 | 노드 내부의 가상 브리지를 통해 통신 |
| 다른 노드의 파드끼리 | 노드를 넘어가는 네트워크가 필요    |

- 쿠버네티스는 규칙만 정하고 구현은 CNI 플러그인에 맡김
	- 대표적인 CNI 플러그인: 플라넬, Calico, Cilium

> [!note]+ 파드의 IP 주소는 변하지 않는가
>
> - 파드의 IP 주소는 고유하지만 고정되어 있지는 않음
>     - 파드가 다시 만들어지면 새 IP 주소를 받음
> - 그래서 파드의 IP로 직접 접속하지 않고, 변하지 않는 엔드포인트인 서비스를 통해 접속함
>     - 서비스가 레이블로 대상 파드를 찾아 현재 IP로 전달

## 플라넬이란
- 플라넬(flannel): 노드들을 잇는 오버레이 네트워크를 만들어 파드 간 통신을 구현하는 CNI 플러그인

## flanneld란
- 각 노드에서 동작하는 플라넬의 에이전트 프로그램
- 각 노드에 고유한 서브넷을 할당
- 네트워크 구성이나 서브넷 정보를 기록하고 저장

## 플라넬과 서비스의 차이

| 구분  | 플라넬                       | 서비스                  |
| --- | ------------------------- | -------------------- |
| 목적  | 다른 노드에 있는 파드끼리 IP로 통신하게 함 | 파드에 접속하기 위한 엔드포인트 제공 |
| 계층  | 통신 기반 기술                  | 그 토대 위에서 동작          |

# 로드 밸런싱과 헬스 체크: 정상이 아닌 컨테이너에 요청을 보내지 않아 가용성을 높인다.
## 가용성이란
- 가용성: 시스템이 멈추지 않고 계속 서비스를 제공할 수 있는 정도
- 가동률 = 시스템 정상 가동 시간 ÷ 전체 시스템 가동 시간
- SPOF(Single Point Of Failure, 단일 장애 지점): 이 지점이 멈추면 시스템 전체가 멈춤
- 가용성을 높이는 기본 방법: 이중화 + 장애 감지 후 자동 전환

## 쿠버네티스의 로드 밸런싱
- 쿠버네티스는 서비스(Service) 방식으로 로드 밸런싱을 수행
- 클러스터 안에 서비스를 만들면 엔드포인트가 되는 IP 주소가 생성됨
- 이 IP를 대상으로 한 패킷은 서비스 뒤의 파드로 전달됨
- 서비스 뒤에 파드가 여럿이면 순서대로 각 파드에 패킷을 전달
	- 라운드 로빈(RR, Round Robin)

| 구성 요소      | 역할                                   |
| ---------- | ------------------------------------ |
| iptables   | 네트워크 주소 변환 기능으로 패킷을 파드로 전달           |
| kube-proxy | 에이전트 프로그램, 패킷 전송 방법을 정하는 규칙을 필요에 따라 변경 |

### 패킷 전달 흐름
1. 워커의 kube-proxy가 마스터의 kube-api-server에서 패킷 전송 규칙을 취득
2. kube-proxy가 취득한 정보로 iptables를 변경
3. iptables가 패킷의 주소를 바꿔 해당 파드로 보냄

### iptables와 IPVS
- iptables 대신 IPVS를 쓸 수 있음
- 서비스 수가 10,000개를 넘는 대규모 클러스터에서는 IPVS가 적합
- netfilter: 패킷 필터링과 네트워크 주소 변환을 수행하는 리눅스 기능

| 구분  | iptables                       | IPVS                               |
| --- | ------------------------------ | ---------------------------------- |
| 정체  | 리눅스의 네트워크 관리 도구, netfilter 설정을 변경 | 리눅스 커널에 내장된 로드 밸런싱 기능              |
| 기반  | netfilter                      | netfilter                          |
| 속도  | 상대적으로 느림                       | 설정 내용을 해시 테이블에 보존, 커널 모드에서 동작하여 더 빠름 |

## 쿠버네티스의 헬스 체크
- 워커 노드의 에이전트인 kubelet이 같은 시스템에서 실행 중인 파드의 상태를 정기적으로 확인

| 확인 방법   | 정상으로 판단하는 기준                             |
| ------- | ---------------------------------------- |
| 명령어 실행  | 파드의 컨테이너에서 지정한 명령어를 실행해 성공(종료 코드 0)하면 정상 |
| TCP 통신  | 연결이 가능하면 정상                              |
| HTTP 통신 | 상태 코드가 200대 또는 300대면 정상                  |

- 판단 결과에 따라 파드를 다시 시작하거나, 서비스에서 요청 전송을 중지함
	- 클러스터를 정상 상태로 유지

# 스케일링: 요청 규모에 따라 컨테이너를 늘리거나 줄인다.
## 스케일링하는 방법
- 메트릭(metrics): 스케일링을 수행할지 결정하는 데 쓰는 데이터
- 요청 건수 등의 데이터를 정기적으로 취득하고, 임곗값보다 높거나 낮으면 리소스를 늘리거나 줄임
- 현재 데이터뿐 아니라 과거 데이터를 참조하여, 임곗값을 연속으로 넘거나 밑돌 때 증감하는 경우도 있음

| 구분   | 수평 스케일링        | 수직 스케일링          |
| ---- | -------------- | ---------------- |
| 방법   | 리소스 수를 늘리거나 줄임 | 리소스 성능을 높이거나 낮춤 |
| 늘릴 때 | 스케일 아웃         | 스케일 업            |

- 일반적으로 수평 스케일링이 수직 스케일링보다 리소스와 처리 능력의 관계가 선형(비례)에 가까움

> [!note]+ 웹 서버에 수직보다 수평 스케일링을 주로 쓰는 이유
>
> - 수직 스케일링은 노드 한 대의 성능이 상한이고, 적용할 때 파드를 다시 만들어야 함
> - 수평 스케일링은 파드를 추가하기만 하면 되므로 무중단으로 늘릴 수 있음
>     - 여러 개로 분산되어 일부가 멈춰도 서비스가 유지됨
> - 단, 세션 같은 상태를 파드 안에 두지 말고 외부 저장소에 두어야 어느 파드가 요청을 받아도 같은 결과를 낼 수 있음

## 쿠버네티스에서 파드의 수평 스케일링
- HPA(Horizontal Pod Autoscaler): 파드를 수평 스케일링
- HPA 컨트롤러가 주기적으로(기본 15초 간격) 파드의 메트릭을 취득
- 이를 바탕으로 필요한 파드 수를 계산하여 ReplicaSet과 Deployment의 파드 수를 변경
- 기본 메트릭은 CPU 사용률
	- 필요하면 다른 지표를 커스텀 메트릭으로 쓸 수 있음

### 필요한 파드 수를 계산하는 절차
1. `필요한 파드 수 = 현재 파드 수 × (현재 CPU 사용률 ÷ 예상 CPU 사용률)`
2. 필요한 파드 수의 소수점 이하를 반올림

## 쿠버네티스에서 파드의 수직 스케일링
- VPA(Vertical Pod Autoscaler): 파드를 수직 스케일링
- 파드에 할당하는 리소스(CPU, 메모리 등)의 양은 request와 limit 두 파라미터로 정해짐

| 파라미터    | 의미       |
| ------- | -------- |
| request | 리소스의 하한선 |
| limit   | 리소스의 상한선 |

- VPA는 리소스 소비량에 따라 request와 limit을 자동으로 조정
- HPA는 쿠버네티스에 표준으로 탑재됨
- VPA는 베타 버전(2022년 10월 기준)
	- 사용하려면 GitHub에서 내려받아 설치해야 함

## 클러스터 자체의 수평 스케일링
- CA(Cluster Autoscaler): 노드(서버) 수를 늘리거나 줄여 클러스터 자체를 수평 스케일링
- 퍼블릭 클라우드(AWS, Azure 등)에 구축된 쿠버네티스 클러스터에서 사용 가능
- CA가 서버를 늘리는 타이밍은 HPA와 다름

| 동작      | 조건                                         |
| ------- | ------------------------------------------ |
| 서버 수를 늘림 | 리소스 부족으로 파드를 시작하지 못한 경우                    |
| 서버를 폐기  | 한 서버의 리소스 사용률이 낮은 상태가 일정 시간(기본 10분) 계속된 경우 |

- `리소스 사용률 = 요청된 CPU 및 메모리 사용량 ÷ 사용 가능한 CPU 및 메모리 사용량`
	- 임곗값(기본값 50%)을 밑돌면 리소스 사용률이 낮다고 판단

| 도구  | 대상      | 방향  | 조정하는 것           |
| --- | ------- | --- | ---------------- |
| HPA | 파드      | 수평  | 파드 수             |
| VPA | 파드      | 수직  | request와 limit   |
| CA  | 클러스터    | 수평  | 노드 수             |

# 쿠버네티스의 주요 명령어: 매니페스트에 원하는 상태를 적고 kubectl로 전달한다.
## 선언형 기술로 클러스터 조작
- 매니페스트(manifest): 객체의 원하는 상태를 적은 YAML 파일
- 원하는 상태를 적은 매니페스트를 `kubectl apply`로 적용하는 선언형 방식이 기본

## 매니페스트에서 객체를 선택하는 방법
- 레이블(label): 객체에 붙이는 키-값 쌍
	- 예: `app: web`
- 셀렉터(selector): 레이블 조건으로 대상 객체를 고름

## 파드의 생성/확인/명령어 실행/변경/삭제

```bash
kubectl apply -f pod.yaml          # 생성 (변경 시에도 동일)
kubectl get pods -o wide           # 목록 확인 (IP·노드 포함)
kubectl exec -it web -- /bin/bash  # 컨테이너 안에서 명령어 실행
kubectl delete pod web             # 삭제
```

# 자동 빌드: 프로그램을 변경하는 절차를 자동화한다.
## 자동 빌드란
- 소스 코드가 변경되면 컴파일, 테스트, 컨테이너 이미지 생성을 자동으로 수행하는 것
- 코드를 저장소에 푸시하는 것이 트리거가 됨

## 자동 배포란
- 프로그램을 자동으로 릴리스하는 것
- 업로드, 데이터베이스 구조 변경 같은 작업이 필요함

## 이미지 생성부터 배포까지의 절차
1. 이미지 생성
    - 도커 파일(Dockerfile)로 이미지 생성
2. 레지스트리 등록
    - 새로 만든 이미지를 레지스트리에 푸시
3. 배포 업데이트
    - 클러스터에 변경된 이미지를 반영

## 새로운 파드로 변경하는 방법

| 방식      | 내용                     | 특징                |
| ------- | ---------------------- | ----------------- |
| 재생성     | 기존 파드를 모두 정지한 뒤 새 파드를 기동 | 단순하지만 중단이 발생       |
| 롤링 업데이트 | 기존 파드를 조금씩 새 파드로 교체     | 기존 파드와 새 파드가 뒤섞임   |

## 자동 빌드/배포를 지원하는 도구
- 젠킨스 X(Jenkins X), Skaffold, 스피내커(Spinnaker) 등

- 컨테이너 이미지와 매니페스트만 있으면 다른 클라우드의 클러스터에도 그대로 배포할 수 있음
	- 같은 매니페스트와 이미지 => EKS(AWS), GKE(GCP), AKS(Azure), 온프레미스 클러스터

# 쿠버네티스의 아키텍처: 클러스터를 제어하는 마스터와 컨테이너를 실행하는 워커
## 쿠버네티스 아키텍처
- 쿠버네티스에는 마스터와 워커 두 유형의 노드가 있음
- 사용자는 kubectl 명령어 등으로 마스터에 명령을 보내고, 마스터는 그 명령에 따라 워커를 조작
- 마스터와 워커는 여러 구성 요소를 실행하며, 이를 연동하여 오케스트레이션을 수행

## 쿠버네티스 클러스터를 조작하는 방법

| 방법              | 내용                                                    |
| --------------- | ----------------------------------------------------- |
| kubectl 명령어     | 명령줄 인터페이스, 명령을 실행하여 클러스터를 조작                         |
| 대시보드(dashboard) | 웹 기반 GUI, 클러스터를 조작하고 파드의 CPU 사용률 같은 통계를 그래프로 보여줌     |
| 쿠버네티스 API       | 쿠버네티스가 제공하는 API, 이 API로 마스터에 요청을 보내 클러스터를 조작         |

- kubectl 명령어와 대시보드는 내부적으로 쿠버네티스 API를 사용
- 프로그램 등에서 접근할 때는 쿠버네티스 API가 적합

## 마스터의 구성 요소

| 구성 요소                   | 역할                                               |
| ----------------------- | ------------------------------------------------ |
| kube-api-server         | 사용자와 워커가 클러스터와 상호 작용할 수 있는 엔드포인트(REST API)를 제공   |
| etcd                    | 클러스터 관련 설정 등 데이터를 저장하는 장소                        |
| kube-scheduler          | 파드를 시작할 노드를 계획하는 스케줄러, 필요한 리소스 등 조건을 고려해 최적 노드를 결정 |
| kube-controller-manager | 디플로이먼트 컨트롤러 같은 여러 컨트롤러의 실행과 정지를 관리, 클러스터를 정상 상태로 유지 |

### etcd
- 여러 노드로 구성된 키-값 저장소
	- 일부 노드가 고장 나도 데이터가 손실되거나 불일치하지 않는 구조
- kube-api-server와 etcd는 프런트엔드와 백엔드 관계
- kube-api-server는 데이터를 직접 갖지 않고 etcd를 통해 데이터를 관리

## 워커의 구성 요소
- 컨테이너를 시작하는 데 필요한 컨테이너 런타임(도커, 크라이오 등)을 실행
- kubelet과 kube-proxy라는 두 에이전트 프로그램을 실행

| 구성 요소      | 역할                                                                    |
| ---------- | --------------------------------------------------------------------- |
| kubelet    | 마스터에서 PodSpec(파드의 상태를 나타내는 데이터)을 가져온 뒤, 컨테이너 런타임 인터페이스에 접근해 컨테이너를 실행·정지·감시 |
| kube-proxy | 마스터에서 네트워크 구성을 가져온 뒤, 파드끼리 통신할 때 접근을 중계하고 주소 변환 규칙을 변경                |

### 구성 요소 간의 흐름
- 마스터의 etcd, kube-scheduler, kube-controller-manager는 모두 kube-api-server와 연결됨
- kube-api-server => (네트워크 구성) => kube-proxy => iptables(주소 변환) 변경
- kube-api-server => (PodSpec) => kubelet => 컨테이너 런타임 => 파드(컨테이너) 실행·정지·감시

> [!note]+ 모든 구성 요소가 API 서버만 거쳐서 통신하는 이유
>
> - 상태를 읽고 쓰는 경로가 한곳으로 모이면 인증, 권한 검사, 검증을 한곳에서 할 수 있음
>     - etcd의 일관성을 지키기 쉬움
> - 각 구성 요소는 서로를 직접 호출하지 않고, API 서버의 변화를 지켜보며 자기 일만 하므로 서로 독립적임
> - 구성 요소 하나가 잠시 멈춰도 다시 살아나면 현재 상태를 보고 이어서 처리할 수 있음
