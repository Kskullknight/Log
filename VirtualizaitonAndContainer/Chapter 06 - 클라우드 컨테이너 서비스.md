# 클라우드의 컨테이너 지원 현황
## AWS
- ECS(Elastic Container Service): 아마존 고유의 컨테이너 오케스트레이션 서비스
- EKS(Elastic Kubernetes Service): 관리형 쿠버네티스 서비스
- Fargate: 서버 관리 없이 컨테이너를 실행하는 서버리스 실행 환경
	- ECS와 EKS의 실행 기반으로 사용
- ECR(Elastic Container Registry): 컨테이너 이미지 저장소
- 독자 방식(ECS)과 표준 방식(EKS)을 둘 다 제공하는 것이 특징

## GCP
- GKE(Google Kubernetes Engine): 관리형 쿠버네티스 서비스
	- 쿠버네티스를 만든 구글이 제공
- Cloud Run: 컨테이너 이미지를 올리면 바로 실행하는 서버리스 실행 환경
	- 요청이 없으면 0까지 축소
- Artifact Registry: 컨테이너 이미지와 패키지 저장소
	- 이전의 Container Registry의 후속
- Anthos: 온프레미스와 다른 클라우드의 클러스터까지 통합 관리
- 독자 오케스트레이션 서비스 없이 쿠버네티스 중심으로 구성

## Azure
- AKS(Azure Kubernetes Service): 관리형 쿠버네티스 서비스
- ACI(Azure Container Instances): 서버 없이 컨테이너(그룹)를 바로 실행하는 서버리스 실행 환경
- ACR(Azure Container Registry): 컨테이너 이미지 저장소
- AKS와 ACI를 가상 쿠블릿으로 연결하여 함께 사용할 수 있음

## 각 클라우드에서 제공하는 컨테이너 서비스

| 분류         | AWS     | GCP               | Azure |
| ---------- | ------- | ----------------- | ----- |
| 독자 오케스트레이션 | ECS     | -                 | -     |
| 관리형 쿠버네티스  | EKS     | GKE               | AKS   |
| 서버리스 컨테이너  | Fargate | Cloud Run         | ACI   |
| 레지스트리      | ECR     | Artifact Registry | ACR   |

### 관리형 서비스에서 사업자가 맡는 범위

| 구분      | 직접 구축 | 관리형 쿠버네티스   | 서버리스 컨테이너 |
| ------- | ----- | ----------- | --------- |
| 컨테이너    | 이용자   | 이용자         | 이용자       |
| 워커 노드   | 이용자   | 이용자(일부 자동화) | 사업자       |
| 컨트롤 플레인 | 이용자   | 사업자         | 사업자       |
| 물리 인프라  | 이용자   | 사업자         | 사업자       |


## 클라우드 서비스 선택 시 주의점
- 컨테이너 서비스의 내용
- 가격
- 정보 보안 관리 시스템
- 플랫폼 간 마이그레이션

### 어떤 클라우드 서비스를 사용해야 할까

| 상황                            | 어울리는 선택                            |
| ----------------------------- | ---------------------------------- |
| 이미 쓰고 있는 클라우드가 있음             | 그 클라우드의 서비스(기존 네트워크·권한·감시 체계와 연계)  |
| 쿠버네티스 지식·자산을 활용하고 멀티 클라우드를 고려 | 관리형 쿠버네티스(EKS, GKE, AKS)           |
| AWS만 쓰고 단순하게 운영               | ECS                                |
| 노드 관리 없이 컨테이너만 실행             | 서버리스 컨테이너(Fargate, Cloud Run, ACI) |
| 요청량 변동이 크고 한가한 시간이 김          | 0까지 축소되는 Cloud Run 등               |

- 기능 차이보다 기존 환경, 팀의 기술, 운용 부담, 비용이 판단 기준이 됨

# 아마존 ECS
## 아마존 ECS란
- 아마존 고유의 컨테이너 오케스트레이션 서비스
	- 쿠버네티스 없이 AWS 안에서 컨테이너를 배치하고 관리
- 컨테이너의 배치, 실행, 확장, 복구를 AWS에 맡겨 자동화할 수 있다.
- 로드 밸런서(ELB), 권한(IAM), 네트워크(VPC), 관측(CloudWatch) 등 AWS 서비스와 긴밀하게 연계

## 아마존 ECS의 작동 방식

| 구성 요소  | 내용                                | 쿠버네티스 대응      |
| ------ | --------------------------------- | ------------- |
| 클러스터   | 태스크와 서비스가 실행되는 논리적 그룹             | 클러스터          |
| 태스크 정의 | 사용할 이미지, CPU·메모리, 포트, 환경 변수 등을 정의 | 매니페스트(파드 템플릿) |
| 태스크    | 태스크 정의로 실행된 컨테이너의 묶음              | 파드            |
| 서비스    | 태스크를 지정한 개수만큼 유지하고 로드 밸런서와 연결     | 디플로이먼트 + 서비스  |

- 태스크 정의 => 서비스(원하는 태스크 수 지정) => 클러스터 안에서 태스크 실행
	- 태스크 하나가 멈추면 서비스가 새로 실행함

> [!note]+ 태스크와 서비스의 구분
>
> - 태스크를 단독으로 실행하면 처리가 끝나거나 멈췄을 때 그대로 종료됨
> - 서비스는 지정한 수의 태스크가 항상 실행되도록 감시함
>     - 태스크가 멈추면 새로 실행하고 로드 밸런서에 등록까지 해줌

### 시작 유형
- EC2
	- EC2 인스턴스 기반으로 이용자가 관리
- Fagate
	- AWS가 관리하는 서버리스 기반

## 아마존 ECS의 장단점
### 장점
- AWS 서비스와 연계가 쉬움
- CodePipeline과 CodeCeploy를 이용하여 자동 빌드/배포 가능

### 단점
- 쿠버네티스 생태계(헬름, 오퍼레이터 등)의 도구를 쓸 수 없음
- 쿠버네티스보다 세밀한 제어와 확장 기능이 적음

# 아마존 EKS
## 아마존 EKS란
- AWS에서 쿠버네티스 클러스터를 손쉽게 실행할 수 있게 해주는 관리형 서비스
- 컨트롤 플레인을 AWS가 운영하고, 이용자는 표준 쿠버네티스를 그대로 사용
- 쿠버네티스 적합성 인증을 받은 표준 쿠버네티스
	- 기존 매니페스트, kubectl, 헬름 등을 그대로 쓸 수 있음
- 마스터(컨트롤 플레인)의 구축, 이중화, 패치, 업그레이드를 AWS가 담당
- IAM(인증), VPC(네트워크), ELB(로드 밸런서), EBS(스토리지) 등 AWS 서비스와 연계

## 아마존 EKS의 작동 방식
- kubectl => 컨트롤 플레인(AWS 관리) => 워커 노드 => 파드
	- 컨트롤 플레인: API 서버, etcd, 스케줄러
	- 워커 노드: EC2 또는 Fargate(서버리스)
- 워커 노드는 이용자의 VPC 안에서 실행됨

## 리전과 가용 영역
- 리전
	- 데이터 센터가 모여 있는 지리적 지역
- 가용 영역
	- 리전 안에서 전원과 네트워크가 서로 독립된 데이터 센터 그룹

- EKS의 컨트롤 플레인은 한 리전의 여러 가용 영역에 분산 배치됨
	- 한 영역에 장애가 나도 계속 동작
	- AWS가 자동으로 분산

- 워커 노드도 여러 가용 영역에 나누어 두면 영역 장애에 대비할 수 있음
	- 이용자가 직접 분산 배치

## 아마존 EKS의 장단점
### 장점
- 표준 쿠버네티스이므로 이식성이 좋고 생태계를 활용할 수 있음
- AWS 서비스와 연계

### 단점
- 워커 노드, 애드온, 버전 업그레이드는 이용자가 챙겨야 함
- ECS보다 구성이 복잡함

# AWS Fargate
## AWS Fargate란
- AWS의 서버리스 컨테이너 실행 환경
- 컨테이너를 실행할 서버를 AWS가 대신 준비하고 관리해 주는 실행 기반
	- 서버(EC2)를 준비하거나 관리하지 않고 컨테이너만 실행
- 단독 서비스가 아니라 ECS·EKS의 실행 기반으로 선택해서 사용
- 이용자는 태스크(파드)에 필요한 vCPU와 메모리만 지정
	- 서버 종류, 대수, OS 패치는 신경 쓰지 않음

## AWS Lambda와 차이점
- 둘 다 서버리스지만 실행 단위와 실행 방식이 다름

| 구분       | AWS Fargate           | AWS Lambda                      |
| -------- | --------------------- | ------------------------------- |
| 분류       | 서버리스 컨테이너             | 서버리스 함수(FaaS)                   |
| 실행 단위    | 컨테이너(태스크)             | 함수                              |
| 실행 방식    | 기동 후 계속 실행, 상시 대기 가능  | 이벤트가 발생할 때만 실행                  |
| 실행 시간    | 제한 없음                 | 최대 15분                          |
| 실행 환경    | 컨테이너 이미지로 자유롭게 정의     | 지원 런타임 중심(컨테이너 이미지도 가능하나 제약 있음) |
| 확장       | 태스크 수 조정(자동 확장 설정 필요) | 요청 수에 따라 자동                     |
| 과금       | 태스크 실행 시간 × vCPU·메모리  | 요청 횟수 + 실행 시간 × 메모리             |

### 어울리는 용도
- Fargate
	- 상시 요청을 받는 API 서버
	- 15분 이상의 걸리 작업
- Lambda
	- 이벤트에 따른 간단한 처리
	- 15분 미만의 간단한 처리

# GKE
## GKE란
- GKE(Google Kubernetes Engine)
	- 구글 클라우드에서 쿠버네티스 클러스터를 실행하고 관리해 주는 서비스
- 컨트롤 플레인의 구축, 이중화, 업그레이드를 구글이 담당
- 주요 클라우드 중 가장 먼저 나온 관리형 쿠버네티스 서비스

## GKE의 작동 방식
- kubectl => 컨트롤 플레인(구글 관리) => 노드 풀 => 노드(VM) => 파드
- 노드: Compute Engine의 가상 머신
- 노드 풀: 머신 유형 등 같은 설정을 가진 노드의 그룹
	- 용도별로 나누어 구성
## 리전과 영역
- 리전
	- 데이터 센터가 모여 있는 지리적 지역
- 영역
	- 리전 안의 독립된 구역
	- AWS의 가용 영역에 해당

### 영역에 따른 클러스터 유형
- 단일 영역 클러스터
	- 하나의 영역에 클러스터 마스터와 노드를 구성
- 다중 영역 클러스터
	- 하나의 영역에 클러스터 마스터와 여러 영역의 노드로 구성
- 리전 클러스터
	- 여러 영역에 클러스터 마스터와 여러 영역의 노드 구성

## 쿠버네티스는 GKE가 가장 좋을까
- 쿠버네니스 구글에서 개발하였기 때문에 세세한 부분에서 뛰어남
	- 자동 업데이트
	- 노드 자동 업데이트
- 그러나 무조건 GKE가 정답은 아님

# 클라우드 런
## 클라우드 런이란
- Cloud Run: 컨테이너 이미지를 배포하면 실행, 확장, HTTPS 주소 제공까지 자동으로 해주는 완전 관리형 서비스
	- 서버나 클러스터 없이 바로 실행
- 컨테이너로 만들 수 있으면 언어와 라이브러리에 제한이 없음
- 컨테이너는 환경 변수 `PORT`로 지정된 포트에서 요청을 받아야 함

## 클라우드 런의 작동 방식
1. 컨테이너 이미지를 배포하면 서비스가 만들어짐
    - 서비스마다 고유한 HTTPS URL이 부여됨
2. 배포할 때마다 리비전이 생성됨
3. 요청이 늘어나면 인스턴스가 자동으로 늘어남
4. 요청이 없으면 인스턴스가 0개가 됨
    - 과금 없음

- 트래픽 분할: 리비전별로 요청 비율을 지정
	- 새 버전 10%, 기존 버전 90%처럼 나누어 카나리 배포에 사용
- 동시 실행 수: 인스턴스 하나가 동시에 처리할 요청 수를 설정
	- 이를 넘으면 인스턴스가 추가됨

## 클라우드 런의 장점과 단점
- 장점
	- 클러스터와 노드 관리가 필요 없음
	- 요청만큼만 과금된
- 단점
	- 제어 범위가 한정됨


> [!note]+ Cloud Run과 Cloud Functions(FaaS)의 차이
>
> - Cloud Functions: 함수 코드만 올리고 실행 환경은 구글이 정한 런타임을 사용
> - Cloud Run: 컨테이너 이미지를 올리므로 언어, OS 패키지, 라이브러리를 자유롭게 고를 수 있음
>     - 한 인스턴스가 여러 요청을 동시에 처리할 수 있음
> - 둘 다 0까지 축소되고 사용한 만큼 과금됨

## 안토스란
- Anthos: 구글 클라우드, 온프레미스, 다른 클라우드의 쿠버네티스 클러스터를 하나로 통합 관리하는 플랫폼
	- 관리 대상: GCP(GKE), 온프레미스, AWS, Azure
- 하이브리드 클라우드와 멀티 클라우드를 같은 방식으로 운영하기 위한 기반

# AKS
## AKS란
- AKS(Azure Kubernetes Service): 
	- Azure에서 쿠버네티스 클러스터를 배포하고 운영하게 해주는 서비스
- 컨트롤 플레인은 Azure가 운영하고, 이용자는 노드와 애플리케이션만 관리
	- 컨트롤 플레인의 구축, 감시, 유지 보수를 Azure가 담당
- 마이크로소프트 제품군과 연계
- 리눅스 컨테이너뿐 아니라 윈도우 컨테이너 노드도 지원

## AKS의 작동 방식
1. 이용자가 kubectl이나 포털로 컨트롤 플레인에 요청을 보냄
2. 컨트롤 플레인이 파드를 실행할 노드를 정함
    - 컨트롤 플레인은 Azure가 관리
3. 노드 풀에 속한 노드(VM)가 파드를 실행
    - 시스템 노드 풀: 클러스터 필수 파드를 실행
    - 사용자 노드 풀: 애플리케이션 파드를 실행

| 구성 요소    | 내용                                  |
| -------- | ----------------------------------- |
| 컨트롤 플레인  | API 서버, etcd, 스케줄러 등, 요청을 받아 노드를 제어 |
| 노드 풀     | 같은 구성의 노드 그룹                        |
| 노드       | Azure 가상 머신                         |
| 파드       | 실제로 실행되는 컨테이너 묶음                    |
| 시스템 노드 풀 | CoreDNS 등 클러스터 운영에 필요한 파드를 실행       |
| 사용자 노드 풀 | 이용자의 애플리케이션 파드를 실행                  |


- 클러스터 오토스케일러로 노드 수를 자동 조절
- 노드 자동 복구와 업그레이드를 지원

## 리전과 가용 영역
- 리전
	- 데이터 센터가 모여 있는 지리적 지역
- 가용 영역
	- 리전 안에서 독립된 구역

- 클러스터를 만들 때 가용 영역을 지정하면 노드가 여러 영역에 분산 배치할 수 있음

## 가상 쿠블릿이란
- 가상 쿠블릿(Virtual Kubelet): 쿠버네티스의 쿠블릿을 가상으로 구현 한 것
	- 쿠블릿(kubelet): 각 노드에서 파드를 실행하고 관리하는 에이전트
- AWS Fargate나 ACI에서 동작하는 컨테이너로 사용할 수 있다.
# ACI
## ACI란
- ACI(Azure Container Instances)
	- 서버를 따로 준비하지 않고 컨테이너를 바로 실행할 수 있는 Azure 서비스
- 가상 머신을 구축하거나 오케스트레이션 도구를 도입하지 않고, 명령 한 번으로 컨테이너를 실행
- 공인 IP 주소와 DNS 이름을 부여하여 인터넷에 바로 공개할 수 있음

## ACI의 작동 방식
- 컨테이너 그룹: 같은 호스트에서 함께 실행되는 컨테이너의 모음
	- ACI의 기본 단위
	- IP 주소와 DNS 이름은 그룹당 하나

| 컨테이너 그룹의 특징 | 내용                           |
| ----------- | ---------------------------- |
| 공유 자원       | 생명 주기, 네트워크(IP·포트), 스토리지 볼륨  |
| 그룹 내 통신     | localhost로 통신                |
| 쿠버네티스 대응    | 파드(Pod)와 같은 개념              |
| 용도          | 앱 + 로그 수집·감시 등 보조 컨테이너(사이드카) |

- 볼륨: Azure Files 공유를 마운트하여 데이터를 영속화
	- 컨테이너 자체는 상태를 유지하지 않음

## 컨테이너 그룹의 배포 방식
- YAML 파일: 컨테이너 그룹의 구성을 YAML로 기술하여 배포
- ARM 템플릿: Azure 리소스를 JSON으로 정의하는 표준 템플릿

## ACI의 위치
- ACI는 오케스트레이션 도구가 아니라 컨테이너를 실행하는 가장 단순한 부품

# 도커 엔터프라이즈
## 도커 엔터프라이즈란
- Docker Enterprise:
	- 도커 엔진에 클러스터 관리, 보안, 이미지 관리 기능과 기술 지원을 더한 기업용 유료 제품
- 특정 클라우드의 서비스가 아니라 소프트웨어 제품
	- AWS, Azure, GCP, 온프레미스 어디에나 설치할 수 있음
- 어느 환경에서든 같은 플랫폼과 같은 조작으로 컨테이너를 운영
	- 멀티 클라우드와 하이브리드 클라우드를 구성할 수 있음
- 오케스트레이션 도구로 스웜(Swarm)과 쿠버네티스를 모두 지원
	- 한 클러스터에서 함께 사용할 수 있음
- 구조: 중앙 관리 화면(웹 UI·API·접근 제어) => 각 환경의 클러스터(도커 엔진 + 스웜/쿠버네티스)

## 도커 엔터프라이즈에서 사용 가능한 도구

| 도구(당시 명칭)                    | 역할                                      |
| ---------------------------- | --------------------------------------- |
| Docker Engine - Enterprise   | 기업용 컨테이너 런타임, 보안 강화·인증·장기 지원 제공         |
| UCP(Universal Control Plane) | 클러스터 중앙 관리, 웹 UI·스웜과 쿠버네티스의 통합 운영·접근 제어 |
| DTR(Docker Trusted Registry) | 사내 전용 레지스트리, 이미지 저장·취약점 검사·서명           |
