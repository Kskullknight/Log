# 요구사항 개요
- 정의
	- 소프트웨어 시스템이 수행해야 할 것과 소프트웨어 시스템에 있어야 할 특성을 기술한 문장
- 특성
	- 소프트웨어 개발 수명 주기의 가장 중요한 요소이며 소프트웨어 개발의 기준이 된다
	- 다양한 스테이크홀더로부터 도출된다
	- 무엇을 표현하는 것이면 어떻게는 포함하지 않는다
	- 기능적 요구사항과 비기능적 요구사항이 있다
	- 고객과 개발자간의 의사소통 수단이 된다
	- 분석과 설계 과정을 거치면서 지속적으로 변화하는 경향이 있다
	- 요구사항의 문제점을 늦게 발견할 수록 수정비용이 많이 발생한다
	- 프로젝트의 실패의 가장 중요한 이유중 하나는 명확하지 못한 요구사항 정의로부터 비롯된다.

>[!note]+ 어떻게(How)를 포함하지 않아야 하는 이유
>- 요구사항은 고객과 개발자 간의 의사소통 수단이기 때문에 개발자만 아는 '어떻게'는 포함하지 않아야 한다.
>	- 고객은 '어떻게'가 좋은지 판단할 수 없다.
>- 요구사항 수준에서 '어떻게'를 고정하는 경우 이후 수정하기 어렵다. 
>	- `요구사항의 문제점을 늦게 발견할 수록 수정비용이 많이 발생한다`
>- 

> [!note+] 구체적인 요구사항은 무엇인가?
> 

## 요구사항 분류
### 기능적 요구사항
- 사용자의 업무 처리와 직접 관련되어 소프츠웨어 시스템이 수행해야하는 요구 내용
- 고려 사항
	- 기능성
	- 데이터
	- 사용자
### 비기능적 요구사항
- 소프트웨어 시스템이 제공해야 하는 행위적 속성
- 관점
	- 운영 요구사항
	- 자원 요구사항
	- 성능 요구사항
	- 보안요구사항
	- 문화적/정책적 요구사항
	- 품질 요구사항
- 특징
	- 초기 단계에서 고려되지 않을 수 있음
		- 설계 과정에서 구현
	- 인터페이스 설계, 데이터 형식 설계, 모듈화 설계등의 관점에서 비기능적 요구사항을 반영해야함
### 인터페이스 요구사항
- 동일한 인터페이스 구조를 유지하기 위해 제시하는 요구사항
## 요구사항 정의 품질
- 부정적 현상이 발생하지 않도록 주의해야 한다
	- 노이즈 발생
		- 관련된 정보가 포함되거나 모호한 표현이 존재하는 경
	- 침묵 발생
		- 누락이 발생한 경우
	- 과도한 스펙 명세
		- 결정되지 않는 구현 솨련 사항이 포함되는 경우
	- 모순
		- 일관성이 없는 경우
	- 모호성
		- 하나의 표현이 여러 가지 의미로 해석되는 경우
	- 전방 참조
		- 정의하지 않은 상황을 참조하는 경우
	- 사실이 아닌 기대 사항
		- 추측과 기대에 근거하는 경우
### 요구사항 정의의 품질 요소
#### 정확성을 갖춘 문서
- 스테이크 홀더들기 원하는 모든 요구가 정의
- 요구들이 기능으로 모두 반영되어 표현되어야함
#### 모호성이 없는 문서
- 모든 요구사항이 한가지 의미로만 해석되어야함
#### 완전성을 갖춘 문서
- 다음 네 가지 사항을 만족함
	1. 시스템이 제공하는 모든 것이 요구사항 정의서에 포함됨
	2. 모든 입력에 대해 구현 가능한 정당한 결과가 제시되어야 한다
	3. 정확히 표현되어야 한다
	4. 문서의 내용상 TBD(To Be Determined)가 나타나지 않아야 한다
#### 일관성을 갖춘 문서
- 현재 분서의 내용이 이전 문서의 내용과 충돌하지 않아야 한다.
- 문서의 세부 절간에 내용상 충돌이 없어야 한다
- 사용되는 모든 용ㅇ어는 표준 용어사전을 기반으로 해야 한다.
#### 추적성을 갖춘 문서
- 변경을 기록하고 추적가능 해야 한다.
##### 추적성 메트릭스
- 문서간의 추적성은 추적성 메트릭스를 활용함
	- 예) 요구사항 정의서 - 요구사항 분석서
		- 어떤 유즈 케이스에 어떤 요구사항(기능적, 비기능적)을 반영하는지 표현
- 구현 단계에서 발생하는 요구사항 변경을 어떻게 처리할지 결정할 때 중요하게 사용
- 변경에 따른 영향 부분을 식별할 수 있다.
# 요구사항 수집 기법
- 사용자로부터 구체적이고 세부적인 요구사항을 확보하기 위한 목적
	- 누구를 대상으로 하는지
	- 어떤  정보를 수집하는지
	- 정보를 어떻게 정리할 것인지
- 요구사항을 정확하게 정의 하는 것은 프로젝트 성공에 주요한 영향을 미침
	- 많은 시간을 들여서 작업할 필요가 있다.

## 대면 수집 방법
- 관련자를 직접 만나 요구사항을 수집하는 방법
- 현행 정보와 새로운 요구 기능을 알 수 있음

- 장점
	- 자세한 설명 가능
	- 다양한 질문 가능
	- 의견 충돌에 대한 조정 가능
- 단점
	- 많은 시간이 걸림
### 인터뷰
- 인터뷰 대상
	- 실무자
	- 운영 요원
	- 관리자
	- 운영자

- 인터뷰 수행 절차
	1. 인터뷰 준비
		- 대상자 선정: 대상자를 선정하고 스케줄 작성
		- 계획 수립: 세부 질문 작성 + 질문 사전 공지
		- 인터뷰 준비: 인터뷰 대상자에 대한 기초 지식 학습
	2. 인터뷰 실시
		- 인터뷰 시작: 소개 + 수행 이유 설명
		- 실시: 대화식으로 진행하며 30분 정도로 하고 1시간을 넘지 않도록 한다.
		- 종료: 내용 정리 + 감사 표시
	3. 정리
		- 결과 정리: 인터뷰를 통해 수집한 정보를 정리 + 미해결 사항이 있는지 정리
		- 결과 공지 및 평가: 결과를 인터뷰 참여자에게 공지
### JAD(Joint Application Development) 세션
- 관리자, 사용자, 개발자가 모여 요구사항 도출을 위하여 상호 토론하는 방법
- 너무 상세하거나 모호한 요구사항 도출은 피해야 한다.
## 비대면 수집 방법
- 설문지나 문서 분석등 통해 요구사항을 수집하는 전략
- 현행 정보만 수집

- 장점
	- 다양한 정보를 수집하기 쉬움
	- 대면방법에 비해 시간이 적게듬
- 단점
	- 깊이 있는 요구사항을 수집하기 힘듬
### 문서 분석
- 업무에서 사용하고 있는 다양한 종류의 문서를 분석하여 구체적인 요구사항을 확보하는 방법
	- 현재 상태의 정보를 수집하는 것이 목적
- 일주일 정도의 시간을 두고 집중적으로 분석하는 것이 좋음
- 전체적으로 문서를 분석한 내용을 체계적으로 정리
	- 필요한 경우 복사본을 수집
### 설문지 활용
- 질문지를 이용하여 다수 사용자에게 배포하고 수집하여 요구사항을 확보
- 중요 사항
	- 설문 대상 선정: 연령, 직업군, 역활 등을 고려하여 대상자 그룹을 선정
	- 설문 문항 작성: 배포하면 수정이 불가능. 초기에 설문을 잘 구조화해야함
	- 설문지 회수 방법: 응답 결과를 회수해야함
#### 설문지 작성시 고려 사항
- 관심있고 쉬운 질문으로 시작
- 관련성있는 질문 내용을 그룹으로 묶어서 구성
- 끝부분에 중요한 설문 내용을 두지 않는다.
- 한 페이지에 너무 많은 설문을 두지 않는다
- 어렵거나 전문적인 용어 사용을 피한다
- 편향된 질문이나 답을 유도하는 형식의 질문은 피한다
- 답의 기재 방법을 판단하기 쉽게 선정한다
- 모든 질문에 고유번호를 부여한다
- 모호한 질문이 없는지 사전 테스트 진행한다
- 정보는 익명으로 처리한다.
### 관찰
- 미래 사용자가 수행하는 활동을 살펴보는 활동
- 중요하다고 생각하지 않은 업무 처리 과정을 찾아내는 것이 목적
	- 또는 요구사항이 적합한지 판단하기 위해 사용
### 소셜 네트워크
- 소셜 네트워크를 이용하여 사용자의 반응이나 의견을 수집
	- 시간과 공간의 제약 없이 다수 사용자에게 요구사항을 수집할 수 있다.
- 장점
	- 다수의 고객에게 다양한 정보를 수집할 수 있다
	- 특정 영역에 대한 질문에 대한 응답을 수집할 수 있다.
- 단점
	- 비정형 데이터로 이루어짐
	- 약어와 비속어가 포함되어 있을 수 있다.
- 자연어 처리 기법등을 이용하여 정보를 추출할 수 있다.
# 요구사항 정의서 작성
- 요구사항을 체계적으로 정리하여 요구사항 정의서를 작성한다.
- 요구사항 정의서
	- 사용자의 요구사항과 개발 관련 요구사항을 정의한 문서
	- 일관성과 정확성을 가지고 작성해야 한다.

## 요구사항 준수사항
- 모든 요구사항에는 유일한 식별자를 부여해야 한다
	- 양과 추적성을 제공하기 위한 키
- 문장의 5형식에 따라 정확히 표현해야 한다
	- 주어 - 서술어 - 보어 - 직접 목적어 - 간접 목적어
- 단문으로 작성되어야 한다.
	- 복문의 경우 요구사항의 만족여부를 결정하기 모호하기 때문
- 우선순위를 부여한다
	- 우선순위는 추후 지연이나 기간이 부족한 경우 제거 대상을 선정할 중요한 기준으로 사용
- 그룹핑하여 체계화 한다.
	- 시스템의 형상을 쉽게 이해할 수 있도록
	- 기능간의 응집력을 높여 모듈화 개념을 적용하기 쉬워진다

- 요구사항은 반드시 명문화하여 관리해야 한다
	- 요구사항 변경을 추적, 관리할 수 있어야 한다
	- 정보의 손실이 발생하지 않을 수 있도록 한다.
