## 객체지향과 UML
### 객체지향 모델링
- 객체지향
	- 실세계의 사물과 개념을 객체로 정의하여 표현하고자 하는 시도
	
- 기존 절차지향: 데이터와 처리 과정을 분리하여 상호 미치는 영향을 최소화하는 것을 목표
- 객체지향: 특정 기능을 수행하기 위한 데이터와 연산을 하나로 묶어서 객체로 표현하는 접근 방법

> [!note]+ 절차지향에서 객체지향으로 주류 페러다임이 바뀐 이유
> 1.  변경의 파급 범위가 객체 내부로 국소화됨
> 2. 사람이 한 번에 이해해야 할 범위가 줄어듭니다.
> 3.  코드의 분해 단위를 변경의 단위와 일치시킨 것이 객체지향이 유지보수에 유리함
> 4. GUI의 등장 + C++와 Java의 등장

- 객체지향의 특징

| 특징        | 설명                                              |
| --------- | ----------------------------------------------- |
| 클래스       | 실세계의 사물을 정의하기 위한 틀. 속성과 연산으로 정의됨                |
| 오브젝트      | 클래스로부터 생성되는 인스턴스, 실제 연산에 사용됨                    |
| 캡슐화와 정보은닉 | 껍질을 씌워 클래스의 속성과 연산을 감추는 것. 필요한 최소한의 정보만 외부로 공개함 |
| 상속        | 구체 클래스들은 공통 속성과 공통 연산을 뽑아내어 추상 클래스로 선언함         |
| 다형성       | 같은 메시지에 대해 어떤 시점에 어떤 객체에 사용되는가에 따라 서로 다른 행위를 가짐 |

- 객체지향의 목적
	- 매우 융통성있는 시스템 모델링과 개발이 가능
	- 코드의 구조 체계화

### UML 모델링 언어
- UML: Unified Modeling Language
	- 다이어그램을 표현하기 위한 기본 모델 요소를 표준적으로 정의한다.
	- 모든 사람이 동일하게 이해할 수 있도록 하기 위함이다.
		- 다이어그램의 유형별 심볼과 그 의미는 OMG(Object Management Group)에서 제시
- UML 다이어그램의 분류 (총 14종)
	- 구조(정적) 다이어그램: 시스템의 구조를 표현
		- 클래스, 객체, 패키지, 컴포넌트, 배치, 합성 구조, 프로필
	- 행위(동적) 다이어그램: 시스템의 동작과 상호작용을 표현
		- 유스케이스, 액티비티, 상태기계, 순차, 커뮤니케이션, 타이밍, 상호작용 개요

> [!note]+ UML이 정의된 이유
> - 객체지향의 확산되면서 다양한 방법론이 등장하면서 다양한 방법론이 만들어짐 => 각 방법론 마다 다른 표기를 사용하여 혼란함
> 	- Booch 방법 (Grady Booch) — 설계 단계에 강점, 구름 모양 표기법
> 	- OMT (James Rumbaugh) — 분석 단계에 강점, 특히 데이터 모델링
> 	- OOSE (Ivar Jacobson) — 유스케이스 개념을 도입, 요구사항 분석에 강점
> - 세사람이 하나의 회사인 Rational Software에 모여서 만듬
> 	- 교육으로 돈 좀 벌었다고함

- 개발 수명주기 단계 마다 사용되는 다이어그램이 다름

| 개발 생명 주기 단계 | 주요 다이어그램                | 사용 목적                                             |
| ----------- | ----------------------- | ------------------------------------------------- |
| 요구사항 분석     | 유스케이스, 액티비티             | - 사용자 관점에서 시스템 기능을 식별<br>- 업무(비즈니스) 흐름을 파악        |
| 분석          | 유스케이스, 클래스, 순차, 상태 기계   | 객체(클래스)의 구조와 객체 간 상호작용, 상태 변화를 분석                 |
| 설계          | 패키지, 클래스, 순차, 타이밍, 컴포넌트 | - 시스템 아키텍처와 모듈(패키지) 구조를 정의<br>- 시간 제약과 물리적 배치를 설계 |
| 구현          | 컴포넌트, 배치                | 소스 코드와 컴포넌트의 관계, 하드웨어 자원으로의 배포 구조를 표현             |
| 테스트         | 유스케이스, 순차, 상태기계         | 시나리오 기반의 테스트 케이스 도출 및 검증                          |

- 분석 단계 모델링 순서
	- 기능 모델링 -> 구조 모델링 -> 행위 모델링

## 기능 모델링
### 기능 모델링 개요
- 기능 모델링이란
	- 사용자로 부터 도출한 요구사항을 입력받아 소프트웨어 시스템이 해야할 기능이 무엇인지를 식별해가는 과정
- UML을 이용하여 분석 결과를 표현

- 요구사항에 대한 충분한 이해가 부족하거나 도메인 지식이 부족한 경우
	- 비즈니스 프로세스에 대한 흐름을 체계적으로 도식화하고, 업무 수행활동간에 전달되는 정보 혹은 객체를 표현한다.
		- 업무 이해를 높이고, 공통된 인식을 갖게하기 위해서 사용
### 유스 케이스 다이어그램
- 시스템의 최상위 수준에 해당하는 기능을 사용자 관점으로 나타내는 것
	- 시스템과 사용자 간에 상호작용을 표현
- 작성 절차
	1. 요구사항 정의 내용을 검토
	2. 요구사항을 토대로 시스템의 경계를 결정
	3. 경계가 설정된 시스템에 대한 명칭을 정의한다.
	4. 시스템 외부에 존재하는 액터를 식별하고 각 액터의 역할을 정의한다.
	5. 각 액터가 시스템에서 사용하는 기능을 식별한다.
	6. 식별된 사용자 기능과 액터간의 관계를 정의한다.
	7. 식별된 사용자 기능에 대한 설명서를 작성한다.

- 액터: 사용자 + 개발 대상 시스템과 상호작용하는 모든 대상
	- 역할 중심으로 식별한다.

- 유즈 케이스를 식별시 고려 사항
	- 시스템이 제공하는 기능을 나타내는 것이어야 한다
	- 사용자가 한 장소에서 일정한 시간에 수행하는 상호 구별되는 비즈니스 프로세스여야 한다.
	- 서로 다른 시간대에 수행되는 행위는 분리하여 각각 별도의 유스 케이스로 식별한다.
	- 유스 케이스는 최초에 액터에 의해 시작된다.
	- 다른 것과 관련 없는 독립된 유스 케이스는 존재할 수 없다
	- 유스 케이스의 이름은 동사구 형태로 기술되어야 한다
	- 하나의 유스케이스는 동작 수행의 종료를 포함하도록 정의해야 한다.
	- 초기 유스 케이스 식별의 실마리는 그룹핑된 요구사항을 하나의 유스 케이스로 매핑하는 것으로 시작할 수 있다.

#### 유스 케이스 간 관계 표시
- 실선
	- 액터와 유스 케이스간의 상호작용을 표시
	- 삼각형: 부모 유스케이스와 자식 유스케이스 간의 상속관계를 표시
- 점선
	- 두 유스케이스간의 확장성을 나타냄
	- 포함 관계: 하나의 유스 케이스에서 반드시 호출되어 실행되어야 하는 동작
		- <<include\>\>
	- 확장 관계: 선택적으로 호출할 수 있는 관계
		- <<extend\>\>
#### 유스 케이스 설명서
- 유스 케이스에 대한 간단한 식별 정보와 유스 케이스 내부에서 처리해야 하는 기능의 상세한 흐름을 나타낸다
##### 유스케이스 식별부
- 포함하는 정보
	- ID
	- 이름
	- 간단한 설명
	- 관련 액터
	- 다른 유스케이스와의 관계
	- 중요도
	- 유스케이스 타입
	- 스테이크 홀더
	- 트리거
##### 정상 시나리오 정의부
- 유스 케이스 내부 기능을 단계별로 작성하는 부분
	- 시스템의 관찰자 입장에서 표현 해야 한다
	- 액터와 시스템간의 상호작용에 초점을 두어야 한다.
	- 시나리오 각 스텝의 문장은 요구사항 정의와 같이 반드시 행위 주체를 포함하여 서술해야 한다.
##### 예외 처리 정의부
- 각 스텝에서 발생 가능한 예외 처리를 작성하는 부분
	- 정상 시나리오의 작성 부분에서 나타나는 식별자와 연결되어 표현한다.

## 구조 모델링
- 소프트웨어가 어떤 구조적 요소들로 이루어 질 수 있는가를 분석하는 과정
	- 사용할 객체와 그들 간의 관계를 정의하는 것
	- 클래스 다이어그램으로 표현
- 비즈니스에서 사용되는 용어들을 이용하여 객체들을 정의함으로써 실세계와 소프트웨어의 의미적 차이를 줄이는 작업이다.
- 설계 단계에서 구조 모델에서 정의된 객체들이 어떻게 생성, 저장, 처리되는지 반영한다.
### 객체 식별
- 기능 모델링에서 작성된 유스케이스 설명서를 이용하여 추상화한 클래스로 정의
- 클래스명 - 속성 - 연산을 정의
#### 문장 분석
- 유스케이스 설명서에 나타난 문장들의 구성 요소를 분석하는 것
	- 각 문장의 품사에 따라 클래스의 구성요소로 매핑한다.
		- 일반 명사 - 클래스
		- 동사 - 연산
			- 소유 동사 - 클래스간 관계
			- 타동사 - 연산
			- 자동사 - 예외처리 연산
		- 고유 명사 -인스턴스 객체
		- 형용사 - 속성
		- 부사 - 연산 or 관계의 속성
#### 일반 객체 목록
- 도메인별로 나타나는 일반적인 용어들을 식별하여 클래스로 사용
	- 물리적으로 존재하는 사물
	- 사건
	- 역할
	- 상호작용
	- 기타: 장소, 조직, 정책등
#### 브레인스토밍
- 프로젝트 관련자들의 생각으로 부터 객체를 추출하여 나열하는 방법
- 주의 할 점: 유스케이스 설명서등을 사전에 검토하지 않아야 한다
	- 이유: 브레인스토밍시 생각에 제한이 생길 수 있기 때문
#### 패턴 적용
- 패턴: 문제를 해결하기 위하여 체계적으로 작성된 클래스와 이들 간의 협업 관계를 정의한 것
	- 객체 간의 관계를 미리 정의해 놓은 것
### 클래스 명세
- 각 클래스에 대한 설명서
- 클래스 명세는 CRC 카드를 이용하여 작성

#### CRC(Class-Responsibility-Collaboration) 구성
##### 기본 정보 명세
- CRC카드의 앞면에 명세되고 클래스에 대한 기본 정보를 표현
	- 클래스 이름
	- 식별자
	- 클래스 타입
		- 구체 or 추상
		- 도메인 or 사용자 인터페이스 등등
	- 클래스 설명
	- 관련 유스케이스 식별자 (Associated Use Case)
	- 클래스의 책임 (Responsibility)
	- 협업 관계 (Collaborator)
##### 속성 및 연산 명세
- CRC 카드의 뒷면에 클래스의 속성과 연산을 정의
	- Attributes: 클래스에 정의하는 멤버 변수
	- Operation: 연산
	- Relationships: 상호 작용하는 다른 클래스
### 클래스 다이어그램 작성
- 소프트웨어의 구조를 나타내는 정적 모델
#### 일반화 관계
- 식별된 클래스를 추상화하여 보다 보편적인 클래스로 나타내는 것
	- 추상 클래스에서 정의된 속성과 연산을 하위의 구체 클래스에서 상속받는 관계
	- Kind of 관계
#### 집합 관계
- 일종의 구성 또는 조합 관계
- 식별된 다수의 클래스가 모여 하나의 집합체를 이룰 수 있음
	- Part of 관계
##### 집약 관계
- 부분이 전체와 독립적으로 존재할 수 있는 약한 결합 관계
- 빈 마름모로 표시
##### 합성관계
- 전체가 소멸하면 부분도 함께 소멸하는 강한 결합 관계
	- 부분은 하나의 전체에만 속한다
- 채워진 마름모로 표시
#### 연관 관계
- 두 클래스간의 일반화, 집합 관계에 속하지 않는 경우 
#### 추가 정보
- 클래스 다이어그램에서 클래스 간 관계와 함께 추가적인 정보를 표현
##### 속성 가시화
- 클래스의 속성으로 정의 되는 변수가 갖는 접근 범위
	- Public (+)
	- Private (-)
	- Protected (#) 
##### 관계 기수성
- 서로 연관을 맺은 두 클래스간에 몇 개의 인스턴스가 발생하는 지 나타냄

| 표기 | 의미 |
| --- | --- |
| 1 | 정확히 1개 |
| 0..1 | 0개 또는 1개 |
| * (또는 0..*) | 0개 이상 |
| 1..* | 1개 이상 |
| n..m | 최소 n개, 최대 m개 |

## 행위 모델링
- 시스템의 내적인 동작을 표현하는 다이어그램
	- 객체간의 발생하는 상호작용 ( Message Passing: 메시지 패싱)
- 메시지 패싱
	- 함수 호출과 동일한 개념
	- 클래스의 인스턴스 수준에서 이루어진다.
- 객체 수준에서 작성됨
### 순차 다이어그램 구성 요소
#### 참여 객체
- 상호작용에 참여하는 객체들을 식별
	- 클래스 다이어 그램에 존재하는 클래스의 객체이어야 한다
- 액터도 참여 객체의 한 유형으로 고려될 수 있다
- 참여 객체간의 상호작용은 일반적으로 왼쪽에서 오른쪽으로 진행한다.
#### 시간 축
- 다이어그램의 세로축은 시간의 흐름을 나타낸다.
	- 위에서 아래로 흐른다
- 업무의 처리 흐름과 동일해야 한다.
- 각 객체가 활성화된 시간을 점선으로 표시한다.
	- 이 점선을 생명선이라고 한다
#### 실행 사건
- 객체는 활성화되어 있는 동안 메시지를 받으면 처리함
- 메시지를 처리하거나 보낼 때 실행 동작 내부에서 발생하는 기간을 사각형으로 표현함
#### 메시지 전달
- 객체간의 상호작용을 나타내는 기본 요소
	- 객체간의 함수 호출을 의미
- 화살표로 호출되는 메소드와 매개변수를 나타낸다

- 메시지의 종류

| 종류 | 표기 | 의미 |
| --- | --- | --- |
| 동기 메시지 | 채워진 화살촉 실선 | 호출 후 응답이 올 때까지 대기 |
| 비동기 메시지 | 열린 화살촉 실선 | 응답을 기다리지 않고 다음 동작 수행 |
| 응답(반환) 메시지 | 점선 화살표 | 처리 결과를 호출한 객체에 반환 |

#### 제어 로직
- 소프트웨어의 행위를 표현
	- 선택, 반복, 병렬 처리등
	- 결합형 심볼로 표현
- 반복적인 기본적인 요소들은 조각을 묶어서 추상화된 개념의 제어 로직으로 표현하는 것
- 다이어그램의 복잡도를 감소시키며 이해도를 높이는 역할
##### Alternative
- 선택을 나타내는 로직
	- 특정 조건을 만족 여부에 따라 서로 다른 행위가 수행될 수 있도록 모델링함
##### Option
- 특정 조건을 만족하는 경우에만 행위를 수행하는 제어 로직
	- 조건을 만족하지 않으면 아무 것도 수행하지 않음 (else가 없는 Alternative)
##### Loop
- 반복 처리를 나타내는 제어 로직
- 최대 반복 횟수를 표현
	- (최소 횟수, 최대 횟수)
##### Parallel
- 정의된 행위들은 병렬로 처리하고자 하는 경우를 나타냄
- 병렬로 실행되는 각 부분을 점선으로 분리
### 순차 다이어그램 작성
- 기능 모델링에서 식별된 유스 케이스 별로 작성한다.

- 고려사항
	- 유스 케이스를 철저하게 분석하고 이해한다
	- 참여할 클래스의 객체를 상단에 나열
		- 왼쪽 부터 Actor - Boundary - Control - Data 객체순으로 나열
			- 실행의 흐름을 왼쪽에서 오른쪽으로 전개되게하기 위함
	- 객체간 메시지의 전달을 시간의 흐름을 기준으로 화살표로 표시
		- 화살표는 상호 교차점이 존재하지 않도록 한다.
	- 제어 로직의 행위에 포함되는 객체는 프래그먼트의 경계선 내에서 모두 포함되어야 한다.

> 여러 단계로 작성하는 이유
	- 복잡한 사용자의 요구사항을 한번에 표현하는 것이 불가능 하기 때문
### 상태기계 다이어그램 작성
- 시스템 상태들의 변화를 모델링하는 수단
	- 한 상태에서 이벤트가 발생하면 다른 상태로 전이하는 동작을 표현

- 객체가 생성되어 소멸될 때까지의 변화를 나타낸다.
- 상태와 상태 사이는 화살표로 연결
	- 상태 전이를 유발하는 이벤트가 레이블 형식으로 부여됨
		- Event\[Guard Condition\]/Action
			- 특정 Event가 주어진 Guard Condition하에 발생하는 다음 Action을 수행하고 상태를 전이한다.
## 분석 산출물 점검
- 설계 과정에서 요구하는 것은 분석과정의 결과물임
	- 따라서 결과물의 일관성을 점검이 이루어질 수 있다
#### 기능 모델과 구조 모델
- 유스케이스 설명서와 CRC 카드 간의 일관성을 점검
- 모든 클래스의 이름은 반드시 유스 케이스 설명서의 어딘가에 나타나야 한다.
- 유스 케이스 설명서에 나타나는 정보들은 클래스의 속성과 연산으로 표현되어야 한다
#### 기능 모델과 행위 모델
- 유스 케이스는 각각 하나의 순차 다이어그램으로 표현되어야 한다.
	- 순차 다이어그램의 개수는 유스케이스 다이어 그램보다 같거나 많아야 한다.
- 유스 케이스 다이어그램의 액터는 순차 다이어그램의 액터이다.
#### 구조 모델과 행위 모델
- 상태 기계 다이어그램은 클래스의 인스턴스와 매핑되어야 한다.
- 순차 다이어그램에서 객체 간에 전달되는 메시지 반드시 클래스의 연산으로 정의되어야 한다.
