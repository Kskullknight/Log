## 모듈화 설계 개요
- 모듈화
	- 독립적인 기능이 있는 논리적 몪음에 대핟아흔 모듈로 소프트웨어 시스템을 구성할 수 있도록 하는 것
	- 모듈화가 개발에서 근본이 되는 이유
		- 이해하기 쉽다
			- 독립적인 기능을 가진 논리적 단위로 나누어지기 때문
		- 팀 단위 개발이 가능해진다
			- 모듈을 기준으로 팀에 작업을 할당가능하다
		- 변경에 의한 수정이 쉽다
			- 영향을 받는 모듈에 국한되어 변경을 반영할 수 있다.
		- 재사용 가능성이 높아진다
			- 독립적인 기능을 가지기 때문에 다른 소프트웨어세 쉽게 사용할 수 있다.
		- 추적성이 높아 진다.
			- ?

- 모듈화 개념은 새발의 전체 수명주기에 걸처 적용할 수 있다.
	- 요구사항
		- 요구사항의 이해를 높이는데 도움을 준다
	- 분석
		- 유스케이스, 클래스등이 모듈의 개념을 가지고 있다.
	- 설계
		- 실질적으로 모듈의 개념이 적용되는 단계

- 좋은 설계의 특징
	- 설계가 계층적인 구조로 나타나야 한다
		- 시스템 -> 서브 시스템 -> 기능 = 모듈
		- 단계적으로 상세화 해야 한다.
	- 설계 결과가 모듈로 구성되어야 한다.
		- 구성 요소는 모듈 개념이 있는 독립적인 컴포넌트들롤 구성되어야 한다.
	- 데이터와 처리 절차가 구분 가능하고 분리된 표현으로 나타나야 한다.
		- 관심사 분리 원리에의해 소트프웨어는 계층화 구조의 형태로 표현하도록 한다.
			- 사용자 인터페이스 -> 처리 -> 데이터
	- 독립적인 특성이 있는 기능 단위로 구현될 수 있도록 한다.
		- 모듈간 또는 외부와 상호작용을 최소화 하는 방향으로 개발해야 한다.

- 좋은 모듈화 구조
	- 상호 관련성이 있는 것 끼리 묶어야 한다.
	- 모듈간의 상호작용이 최소화 되어야 한다.

- 초기 비용은 크지만 이후 적은 비용으로 유지보수가 가능하다.
## 결합력의 이해
- 결합력
	- 모듈간의 의존성 관계

- 결합력이 낮을 수록 좋은 설계가 이루어 졌다는 것을 뜻함
- 설계 과정에서 결합력을 최소화 하는 것을 목표로 함
	- 모듈이 독립적인 기능을 가지도록 함
	- 모듈간의 상호작용을 줄여야함

- 낮은 결함력의 장점
	- 시스템의 구성요소간에 결합이 느슨해진다
	- 변경에 의한 파동효과를 막을 수 있다.
	- 이해도가 높아진다.
	- 인터페이스가 단순해진다.
#### 메시지 결합력
- 결합의 정도가 가장 느슨한 유형
- 객체간의 상호작용을 메시지 전달에 의해서만 이루어짐
> [!note]+ 메시지란 무엇인가?

#### 데이터 결합력
- 기본 데이터 타입을 갖는 변수들에 의해 상호 작용하는 유형
	- 함수 호출
- 폭이 넓은 인터페이스를 정의하지 않는 것이 좋다
	- 직관적인 이해가 어려움
	- 타입이나 순서를 살펴야함
	- 따라서 프로그래머가 실수할 확률이 높음
	- => 구조화된 인터페이스를 사용
#### 스탬프 결합력
- 구조체와 같은 복잡한 데이터를 이용하여 상호작용하는 유형
	- 좋은 모듈 설계 방법에 해당한다?
- 필요한 정보만 전달하는 것이 좋다
	- 실행 시간이나 메모리 사용측면에서 손실
	- 불필요한 의존성 추가
	- 함수관계를 이해하는데 모호해짐
- 서로 관련성이 적은 데이터를 묶지 않도록 조심해야 한다.
#### 제어 결합력
- 매개변수가 함수의 내부 행위를 결정하는 상호작용 유형
- 서로 다른 함수를 호출하도록 변경하는 것이 좋음
#### 외부 결합력
- 2개의 모듈이 외부에 있는 다른 정보를 공유하는 유형
	- 파일, 디바이스 인터페이스, 프로토콜등
- 동시 접근으로 인한 데드락 문제가 발생할 수 있다.
#### 공유 결합력
- 2개의 모듈이 광역 변수를 공유하는 유형
	- 한 모듈의 광역 변수 수정 때문에 다른 모듈이 영향을 받음
		- 의존성 관계가 복잡해짐
#### 내용 결합력
- 한 모듈이 다른 모듈의 내부를 직접 참조하는 유형
	- `goto` 
## 응집력의 이해
- 응집력
	- 모듈을 구성하는 내적 요소 간의 긴으적 관련성의 강도를 측정하는 척도
- 모듈의 응집력을 최대화하는 것을 목표로 한다.
#### 기능 응집력
- 모든 요소가 단지 하나의 기능을 구현하기 위해서 구성되어 있는 유형
	- 다른 추가 연산이나 기승 수행 없이 하나의 기능이 종료
#### 순차 응집력
- 모듈을 구성하는 문장관계에서, 한 문장의 결과가 다른 문장의 입력으로 사용되는 유형
- 매우 좋은 설계이며 유지보수가 용이하다
	- 하지만 마지막 문장이 기능 응집력을 충족하지 못하면 응집력의 효과가 저하된다.
	- 모든 문장이 기능 응집력을 만족하도록 정의해야 한다.
- 모듈을 구성하는 구성 요소간의 관계만을 고려한다.
#### 교환 응집력
- 모듈을 구성하는 모든 요소가 동일한 입력 또는 출력을 사용하는 유형
> [!note]+ 교환 응집력 예시
> - 서로 다른 기능이지만 모두 같은 입력을 사용함 `student`
> ```python
> def process_student_record(student): 
> 	"""교환적 응집: 세 기능이 모두 '같은 데이터(student)'를 사용하지만 
> 	서로의 결과에 의존하지는 않음""" 
> 	# 기능 1: 평균 점수 계산 
> 	average = sum(student["scores"]) / len(student["scores"]) 
> 	# 기능 2: 학생 정보 출력 (같은 student 데이터 사용) 
> 	print(f"이름: {student['name']}, 학번: {student['id']}") 
> 	# 기능 3: 합격 여부 판정 (같은 student 데이터 사용) 
> 	passed = all(score >= 60 for score in student["scores"]) 
> 	
> 	return average, passed 
> ```
> 
>   - 서로 다른 입력을 사용하지만 모든 기능이 하나의 출력인 `report`를 만들고 있다.
>   
> ```python
> def build_monthly_report(sales_data, employee_data, inventory_data): 
>   """교환적 응집: 세 기능이 서로 다른 입력을 사용하지만 
>   모두 '같은 출력(report)'을 생성하는 데 기여함""" 
>   report = {} 
>   # 기능 1: 매출 데이터로 총매출 계산 → report에 기록 
>   report["총매출"] = sum(sales_data) 
>   # 기능 2: 직원 데이터로 인건비 계산 → 같은 report에 기록 
>   report["인건비"] = sum(emp["salary"] for emp in employee_data) 
>   # 기능 3: 재고 데이터로 재고 자산 계산 → 같은 report에 기록 
>   report["재고자산"] = sum(item["price"] * item["qty"] for item in inventory_data) 
> 
> return report
> ```
> 
> - 개선
> 
> ```python
> # 각 함수가 단 하나의 기능만 수행 → 기능적 응집 (가장 높은 응집도) 
> def calculate_total_sales(sales_data): 
> 	"""총매출 계산만 담당""" 
> 	return sum(sales_data) 
> 
> def calculate_labor_cost(employee_data): 
> 	"""인건비 계산만 담당""" 
> 	return sum(emp["salary"] for emp in employee_data) 
> 
> def calculate_inventory_value(inventory_data): 
> 	"""재고자산 계산만 담당""" 
> 	return sum(item["price"] * item["qty"] for item in inventory_data) 
> 
> def build_monthly_report(sales_data, employee_data, inventory_data): 
> 	"""계산된 결과들을 조합하는 역할만 담당""" 
> 	return { 
> 		"총매출": calculate_total_sales(sales_data), 
> 		"인건비": calculate_labor_cost(employee_data), 
> 		"재고자산": calculate_inventory_value(inventory_data), 
> 	}
> ```

#### 절차 응집력
- 모듈을 구성하는 문장들이 의미상 서로 관련이 없지만 제어 흐름의 순서가 있는 유형
	- 기능이 아닌 실행 순서와 관령성이 있도록 구성하는 경우
#### 시간 응집력
- 모듈을 구성하는 각 문장이 실행의 특정 시간과 관련이 있는 유형
	- 관련 없는 기능이 같은 시점에 실행된다는 이유로 묶인 경우
- 예시
	- 데이터를 사용하기 전에 모든 변수를 처음으로 초기화 해야한다
	- 파일을 사용하기 전에 모든 파일을 오픈해둔다
	- 사용자에게 알림 정보를 제공하기 위한 모든 메시지를 처리한다.
#### 논리 응집력
- 논리적으로 같은 유형의 외부 동작들로 구성되는 유형
	- `같은 유형의 일`이라는 이유로 하나로 묶이는 경우
		- 출력이라는 이유로 프린터의 출력과 모니터의 출력을 같은 함수에 두고 플래그로 처리하는 경우
		- 개선 방향
			- 함수 외부에서 경우에 따라 다른 함수를 호출
#### 우연 응집력
- 가장 나쁜 형태의 응집력
	- 절대 작성해서는 안되는 모듈 구성
- 모듈을 구성하는 모든 요소가 아무런 관련성이 없는 것으로 묶인 경우

## 모듈화 응용 기술
### 모듈화와 소모 전력
- 데이터 결합력, 스탬프 결함력, 공유 결함력의 작업 마다 전기 소모량을 측정
	- 머지 소트: 스탬프 > 데이터 > 공유 순서로 나타남
		- 데이터의 이동
	- 허프만 코드: 거의 동일한 결과
		- 수학적 연산
	- => 응용 영역에 따라 다른 결합력을 선택하는 것이 좋을 수 도 있다.
> [!note]+ 어떤 영역에서 어떤 응집도를 선택해야 할까?
> - 성능 관점
> 	  - 데이터 지역성
> 	  - 호출/분기 오버헤드
> 	  - 실행 타이밍 예측성
> - 기능적 응집도 (일반적인 웹 백엔드)
> 	- 컴파일러가 함수 호출을 인라이닝으로 대부분 최적화 해줌
> 	- 유지보수성이 더 중요함
> - 순차적 응집도, 절차적 (데이터 파이프라인)
> 	- 현재의 출력이 다음의 입력이 되는 구조
> 	- 데이터의 지역성을 활용하기 위해서
> - 시간적 응집도
> 	- 임베디드나 펌웨어에서 효율적으로 자원을 사용하기 위해서 사용

### 모듈화와 부채
- 기술적 부채
	- 개발 과정에서 제대로 작어하지 않음ㄴ 추후 이자까지 붙어서 되돌아 온다
- 모듈화를 잘하면 유지보수성이 좋아지고 기술적 부채가 줄어들 수 있다.
	- 하지만 부채를 만들지 않기 위해서 과도한 노력이 들어가면 이 또한 ROI가 높지 않아 손해를 본다
- 좋은 구조일 수록 결합력 보다는 응집력에 더 집중해야 한다.
	- 결합력의 경우 인터페이스 종속성 보다 아키텍처 컴포넌트간의 기능 의존성을 문제를 해결하는데 집중해야 한다.
