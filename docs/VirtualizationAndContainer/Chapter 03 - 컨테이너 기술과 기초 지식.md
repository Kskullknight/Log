## 컨테이너 기술의 역사: 프로세스 격리 기술이 쌓여 컨테이너가 되었다.
### 컨테이너 기술의 역사
- 컨테이너는 도커와 함께 갑자기 나타난 기술이 아님
- 1979년 chroot에서 시작된 프로세스 격리 기술이 쌓여 만들어짐

| 연도        | 기술                         | 내용                                       |
| --------- | -------------------------- | ---------------------------------------- |
| 1979      | chroot                     | 유닉스에서 프로세스가 보는 루트 디렉터리를 바꿈, 파일 시스템 격리의 시작 |
| 2000      | FreeBSD Jail               | 파일 시스템에 더해 프로세스와 네트워크까지 격리               |
| 2001      | Linux-VServer              | 리눅스에서 OS 수준 가상화를 구현                      |
| 2004      | Solaris Containers (Zones) | 격리와 자원 관리를 통합, '컨테이너'라는 이름을 사용            |
| 2005      | OpenVZ                     | 리눅스용 OS 수준 가상화, 커널 패치 방식                 |
| 2006~2008 | cgroups                    | 구글이 개발하여 리눅스 커널에 통합, 프로세스 그룹의 자원 사용량을 제한 |
| 2008      | LXC                        | 네임스페이스와 cgroups를 조합한 리눅스 컨테이너, 표준 커널만으로 동작 |
| 2013      | Docker                     | 이미지, 레지스트리, 간단한 명령으로 누구나 컨테이너를 쓸 수 있게 함  |
| 2014      | Kubernetes                 | 구글이 공개한 컨테이너 오케스트레이션 도구                  |
| 2015      | OCI / CNCF                 | 컨테이너 이미지·런타임 표준화 단체와 클라우드 네이티브 재단 설립     |

#### 발전 흐름
1. 파일 시스템 격리 (chroot)
2. 프로세스·네트워크 격리 (Jail, 네임스페이스)
3. 자원 제한 (cgroups)
4. 이를 조합한 컨테이너 (LXC)
5. 이미지와 배포 방식 (Docker)
6. 대규모 운용과 표준화 (Kubernetes, OCI)

> [!note]+ chroot만으로는 컨테이너라고 할 수 없는 이유
>
> - chroot는 프로세스가 보는 파일 시스템의 루트만 바꿈
> - 프로세스 목록, 네트워크, 사용자는 호스트와 그대로 공유
> - CPU·메모리 사용량을 제한할 수 없음
> - root 권한이 있으면 탈출할 수 있음
> - 네임스페이스(보이는 범위 분리)와 cgroups(자원 제한)가 더해져야 독립된 실행 환경이 됨

### 도커가 바꾼 것
- 격리 기술 자체는 이미 있었고, 도커는 컨테이너의 사용 방법을 바꿈

| 요소                | 내용                           |
| ----------------- | ---------------------------- |
| 이미지               | 애플리케이션과 실행 환경을 하나로 묶어 배포 단위로 만듦 |
| Dockerfile        | 환경 구축 절차를 코드로 기록해 재현할 수 있게 함  |
| 레지스트리(Docker Hub) | 이미지를 공유하고 재사용                 |
| 계층 구조             | 변경된 부분만 저장·전송해 빠르고 가벼움       |

- 초기 도커는 LXC를 이용했고, 이후 자체 런타임으로 교체함
	- libcontainer => runC

### 표준화
- OCI(Open Container Initiative): 컨테이너 이미지와 런타임의 표준을 정하는 단체

| 표준     | 내용                  |
| ------ | ------------------- |
| 이미지 사양 | 컨테이너 이미지의 형식        |
| 런타임 사양 | 컨테이너를 실행하는 방법       |
| 배포 사양  | 레지스트리와 이미지를 주고받는 방법 |

- 표준 덕분에 도커로 만든 이미지를 다른 컨테이너 런타임에서도 그대로 실행할 수 있음

## 컨테이너 기술의 장점: 이미지로 가상 서버를 손쉽게 구축한다. 단, 데이터는 컨테이너에 넣지 않는다.
### 컨테이너 기술의 장점

| 장점       | 내용                                    |
| -------- | ------------------------------------- |
| 가벼움      | 게스트 OS가 없어 이미지가 작고 CPU·메모리 소비가 적음     |
| 빠른 기동    | 프로세스를 시작하는 수준이라 초 단위로 기동              |
| 고밀도      | 같은 서버에 가상 머신보다 훨씬 많이 실행               |
| 이식성      | 이미지만 있으면 PC·서버·클라우드 어디서나 같은 환경으로 동작   |
| 재현성      | Dockerfile로 구축 절차를 코드화해 누가 만들어도 동일    |
| 환경 격리    | 컨테이너마다 라이브러리·버전이 달라도 충돌 없음            |
| 쉬운 확장    | 같은 이미지로 컨테이너를 여러 개 띄워 스케일 아웃          |
| 빠른 배포·롤백 | 이미지 교체로 배포하고, 이전 이미지로 되돌리기 쉬움         |

#### '내 PC에서는 되는데요' 문제 해결
- 기존 방식: 개발·테스트·운영 환경의 OS와 라이브러리 버전이 달라 동작이 달라짐
- 컨테이너: 애플리케이션과 의존성을 이미지 하나로 묶어 그대로 옮기므로 환경 차이가 없어짐

#### 이미지의 계층 구조

| 계층                                  | 특징                        |
| ----------------------------------- | ------------------------- |
| 컨테이너 계층                             | 쓰기 가능, 컨테이너마다 따로 있고 삭제하면 사라짐 |
| 이미지 계층(애플리케이션 코드, 라이브러리·런타임, 베이스 이미지) | 읽기 전용, 여러 컨테이너가 공유        |

- 같은 계층은 여러 이미지와 컨테이너가 공유하여 저장 공간을 아낌
- 변경된 계층만 전송함

### 데이터를 컨테이너에 포함하지 않는다
- 컨테이너는 언제든 버리고 새로 만들 수 있어야 함
- 컨테이너의 쓰기 계층은 임시이므로, 삭제하고 다시 만들면 초기 상태로 돌아감
	- 컨테이너 안에 쓴 데이터는 컨테이너를 삭제하면 함께 사라짐
- 남겨야 할 데이터(DB 파일, 업로드 파일, 로그)는 컨테이너 바깥에 저장해야 함

| 방식         | 내용                               | 용도                  |
| ---------- | -------------------------------- | ------------------- |
| 볼륨         | 컨테이너 엔진이 관리하는 호스트의 저장 영역을 컨테이너에 연결 | DB 데이터 등 영속 데이터     |
| 바인드 마운트    | 호스트의 특정 디렉터리를 컨테이너에 연결           | 개발 중 소스 코드 공유, 설정 파일 |
| 외부 스토리지·서비스 | 네트워크 스토리지, 관리형 DB, 오브젝트 스토리지     | 여러 호스트에서 공유해야 하는 데이터 |

#### 상태 비저장과 상태 저장

| 구분    | 상태 비저장(stateless) | 상태 저장(stateful) |
| ----- | ----------------- | --------------- |
| 내용    | 컨테이너가 데이터를 갖지 않음   | 컨테이너가 데이터를 보유    |
| 교체·확장 | 자유롭게 버리고 늘림        | 데이터 보존·동기화가 필요   |
| 예     | 웹 서버, API 서버      | DB, 파일 저장소      |

- 불변 인프라: 실행 중인 컨테이너를 고치지 않고, 새 이미지를 만들어 통째로 교체하는 사고방식
- 접속 정보 같은 설정 값도 이미지에 넣지 않고 환경 변수로 외부에서 주입

> [!note]+ 컨테이너 안에 데이터를 저장하면 스케일 아웃할 때 생기는 문제
>
> - 컨테이너를 여러 개로 늘리면 컨테이너마다 서로 다른 데이터를 갖게 됨
>     - 1번 컨테이너에만 있는 업로드 파일은 2번 컨테이너로 간 요청에서 보이지 않음
> - 부하가 줄어 컨테이너가 삭제되면 그 데이터도 사라짐
> - 데이터를 외부에 두어야 어느 컨테이너가 처리해도 결과가 같음

## 데브옵스와 컨테이너 기술: 컨테이너가 데브옵스를 기술적으로 뒷받침한다.
### 데브옵스란
- 데브옵스(DevOps): 개발(Development)과 운영(Operations)이 협력하여 소프트웨어를 빠르고 안정적으로 제공하려는 문화이자 방법

#### 개발과 운영의 대립

| 구분        | 개발 팀         | 운영 팀            |
| --------- | ------------ | --------------- |
| 목표        | 새 기능을 빨리 출시  | 서비스를 안정적으로 유지   |
| 변경에 대한 태도 | 변경을 원함       | 변경을 장애 위험으로 봄   |

- 목표가 달라 서로 책임을 떠넘기고 배포가 느려짐
- 두 조직이 같은 목표를 향해 협력하자는 것이 데브옵스

#### 데브옵스의 요소

| 요소  | 내용                              |
| --- | ------------------------------- |
| 문화  | 개발·운영의 공동 책임, 정보 공유, 실패를 비난하지 않고 개선 |
| 자동화 | 빌드·테스트·배포·인프라 구축을 자동화           |
| 측정  | 배포 빈도, 장애 복구 시간 등을 수치로 파악       |
| 공유  | 도구·지식·경험을 팀 간에 공유               |

#### 주요 프랙티스

| 프랙티스           | 내용                                      |
| -------------- | --------------------------------------- |
| CI(지속적 통합)     | 코드 변경을 자주 통합하고 자동으로 빌드·테스트              |
| CD(지속적 전달·배포) | 테스트를 통과한 결과물을 자동으로 배포 가능한 상태로 만들거나 실제 배포 |
| IaC(코드형 인프라)   | 인프라 구성을 코드로 작성하고 버전 관리                  |
| 모니터링           | 운영 상태를 관찰하여 개발에 피드백                     |

- 데브옵스의 순환 흐름
	- 계획 => 코딩 => 빌드 => 테스트 => 릴리스 => 배포 => 운영 => 모니터링 => 다시 계획

> [!note]+ 프랙티스의 약자
>
> - CI: Continuous Integration
> - CD: Continuous Delivery / Continuous Deployment
> - IaC: Infrastructure as Code

### 데브옵스와 컨테이너 기술
- 컨테이너 이미지가 개발과 운영 사이의 공통 전달 단위가 됨

| 데브옵스의 과제          | 컨테이너의 해결                    |
| ----------------- | --------------------------- |
| 개발·운영 환경 차이로 인한 오류 | 이미지에 실행 환경까지 포함하여 어디서나 동일   |
| 환경 구축에 시간이 걸림      | 이미지에서 수 초 만에 기동             |
| 배포 절차가 복잡하고 수작업    | 이미지 교체로 배포, 자동화가 쉬움         |
| 문제 발생 시 복구가 느림     | 이전 버전 이미지로 즉시 롤백            |
| 인프라 구성이 문서·기억에 의존  | Dockerfile·매니페스트로 코드화       |

#### 컨테이너 기반 CI/CD 흐름
1. 개발자가 코드를 저장소에 푸시
2. CI 도구가 빌드·테스트 후 컨테이너 이미지를 생성
3. 이미지를 레지스트리에 등록
    - 버전 태그를 부여
4. 테스트 환경과 운영 환경에 같은 이미지를 배포
5. 테스트를 통과한 이미지가 그대로 운영에 올라감
    - '테스트한 것과 다른 것이 배포되는' 문제가 사라짐

#### 역할 분담

| 역할  | 내용                              |
| --- | ------------------------------- |
| 개발  | 애플리케이션과 실행 환경을 이미지로 정의          |
| 운영  | 이미지를 실행할 기반(오케스트레이션, 감시, 확장)을 제공 |

> [!note]+ 컨테이너를 도입하면 데브옵스가 완성되는가
>
> - 그렇지 않음
> - 데브옵스의 본질은 협력하는 문화와 일하는 방식이고, 컨테이너는 이를 쉽게 해주는 도구
> - 컨테이너를 쓰더라도 조직이 분리되어 책임을 떠넘기거나 배포를 수작업으로 하면 효과가 없음
> - 반대로 컨테이너 없이도 자동화와 협력으로 데브옵스를 실천할 수 있음

## 주요 컨테이너 기술: 컨테이너가 곧 도커는 아니다.
### 도커 이외의 컨테이너 기술
- OCI 표준 덕분에 도커 이외에도 다양한 컨테이너 엔진과 런타임이 존재

| 기술         | 개발          | 특징                                    |
| ---------- | ----------- | ------------------------------------- |
| Podman     | Red Hat     | 데몬 없이 동작, 일반 사용자 권한(루트리스)으로 실행, 도커와 명령어 호환 |
| LXC / LXD  | Canonical 등 | OS 전체를 컨테이너로 실행하는 시스템 컨테이너, 가벼운 가상 머신처럼 사용 |
| containerd | CNCF        | 도커에서 분리된 컨테이너 런타임, 쿠버네티스의 표준 런타임        |
| CRI-O      | Red Hat 등   | 쿠버네티스 전용 경량 런타임                        |
| rkt        | CoreOS      | 보안을 중시한 런타임, 현재는 개발 종료                 |

#### 컨테이너 종류

| 구분    | 애플리케이션 컨테이너         | 시스템 컨테이너         |
| ----- | ------------------- | ---------------- |
| 단위    | 컨테이너 하나 = 프로세스(앱) 하나 | 컨테이너 하나 = OS 환경 전체 |
| 사용 방식 | 버리고 새로 만듦            | 가상 머신처럼 접속해서 관리   |
| 예     | Docker, Podman      | LXC / LXD        |

#### 도커와 Podman

| 구분       | Docker                     | Podman                 |
| -------- | -------------------------- | ---------------------- |
| 구조       | 데몬(dockerd)이 상주하며 컨테이너를 관리 | 데몬 없이 명령이 직접 컨테이너를 실행  |
| 권한       | 데몬이 root로 동작(루트리스 모드도 지원)  | 기본이 루트리스               |
| 단일 장애 지점 | 데몬이 멈추면 영향을 받음             | 없음                     |
| 파드       | 미지원                        | 쿠버네티스처럼 여러 컨테이너를 파드로 묶음 |

### 컨테이너디와 크라이오
- 컨테이너 실행은 여러 계층으로 나뉨
- containerd와 CRI-O는 그중 고수준 런타임에 해당

| 계층      | 역할                               | 예                 |
| ------- | -------------------------------- | ----------------- |
| 컨테이너 엔진 | 사용자 명령 처리, 이미지 빌드                | Docker, Podman    |
| 고수준 런타임 | 이미지 내려받기·관리, 컨테이너 생명 주기 관리       | containerd, CRI-O |
| 저수준 런타임 | 네임스페이스·cgroups를 설정해 실제 컨테이너 프로세스를 생성 | runC, crun        |

- 도커의 실행 흐름
	- docker 명령 => dockerd => containerd => runC => 컨테이너
- 쿠버네티스의 실행 흐름
	- kubelet => (CRI) => containerd 또는 CRI-O => runC => 컨테이너

#### containerd와 CRI-O

| 구분  | containerd              | CRI-O             |
| --- | ----------------------- | ----------------- |
| 출신  | 도커의 내부 구성 요소를 분리해 CNCF에 기증 | 쿠버네티스용으로 처음부터 개발  |
| 용도  | 도커, 쿠버네티스 등 범용          | 쿠버네티스 전용          |
| 특징  | 널리 쓰이고 기능이 풍부           | 필요한 기능만 담아 가볍고 단순 |
| 채택  | 주요 클라우드의 관리형 쿠버네티스      | Red Hat OpenShift |

#### CRI(Container Runtime Interface)
- 쿠버네티스가 컨테이너 런타임을 호출하는 표준 인터페이스
- CRI를 구현한 런타임이면 무엇이든 쿠버네티스에서 사용할 수 있음
- 도커는 CRI를 직접 지원하지 않아 중간 변환 계층(dockershim)이 필요했음
	- 쿠버네티스 1.24에서 제거됨

> [!note]+ 쿠버네티스가 도커 지원을 중단했는데 도커로 만든 이미지를 계속 쓸 수 있는가
>
> - 쓸 수 있음
> - 도커로 빌드한 이미지는 OCI 표준 형식이므로 containerd나 CRI-O가 그대로 실행함
> - 바뀐 것은 쿠버네티스가 컨테이너를 실행할 때 도커 엔진을 거치지 않게 된 것뿐
> - 개발자는 도커로 이미지를 만들고, 운영 환경에서는 containerd가 그 이미지를 실행하는 구성이 일반적

## 마이크로서비스: 애플리케이션을 작고 독립적인 서비스들의 조합으로 구성한다.
### 마이크로서비스와 모놀리스
- 마이크로서비스: 하나의 애플리케이션을 작고 독립적인 서비스들의 조합으로 구성하는 설계 기법
	- 컨테이너와 궁합이 좋음

| 용어      | 내용                                               |
| ------- | ------------------------------------------------ |
| 모놀리스    | 모든 기능을 하나의 애플리케이션으로 만들어 통째로 배포                    |
| 마이크로서비스 | 기능별로 서비스를 나누고, 각 서비스가 API(HTTP/REST, gRPC, 메시지 큐)로 통신 |

- 모놀리스: 회원·상품·주문·결제 기능이 하나의 애플리케이션 안에 있고 하나의 DB를 공유
- 마이크로서비스: 회원, 상품, 주문, 결제가 각각 별도의 서비스이며 서비스마다 DB를 가짐

| 구분    | 모놀리스             | 마이크로서비스           |
| ----- | ---------------- | ----------------- |
| 배포 단위 | 전체를 한 번에         | 서비스별로 독립 배포       |
| 변경 영향 | 작은 수정에도 전체 재배포   | 해당 서비스만           |
| 확장    | 전체를 통째로 복제       | 부하가 큰 서비스만 확장     |
| 장애    | 한 기능의 문제가 전체를 멈춤 | 해당 서비스로 국한할 수 있음  |
| 기술 선택 | 하나의 언어·프레임워크     | 서비스마다 다른 기술을 쓸 수 있음 |
| 데이터   | 하나의 DB를 공유       | 서비스별 DB           |
| 팀     | 큰 팀이 하나의 코드를 공유  | 서비스별 작은 팀이 자율적으로 개발 |
| 초기 개발 | 단순하고 빠름          | 설계·기반 구축 부담이 있음   |

#### 마이크로서비스의 단점

| 단점      | 내용                                    |
| ------- | ------------------------------------- |
| 운용 복잡성  | 서비스 수만큼 배포·감시 대상이 늘어남                 |
| 통신 오버헤드 | 함수 호출이 네트워크 통신으로 바뀌어 지연·실패가 생길 수 있음    |
| 데이터 일관성 | DB가 나뉘어 트랜잭션 처리가 어려움                  |
| 장애 추적   | 요청이 여러 서비스를 거쳐 원인 파악이 어려움, 분산 추적이 필요  |
| 테스트     | 서비스 간 연동 테스트가 복잡                      |

### 마이크로서비스와 컨테이너
- 서비스 하나 = 컨테이너 하나
- 컨테이너의 특성이 마이크로서비스의 요구와 맞아떨어짐

| 마이크로서비스의 요구     | 컨테이너의 특성                      |
| --------------- | ----------------------------- |
| 서비스마다 독립된 실행 환경 | 컨테이너별 격리, 언어·라이브러리가 달라도 충돌 없음 |
| 서비스별 독립 배포      | 이미지 단위로 빌드·배포                 |
| 서비스별 확장         | 필요한 컨테이너만 수를 늘림               |
| 많은 수의 서비스 실행    | 가볍고 고밀도, 가상 머신보다 자원 효율적       |
| 빠른 교체·복구        | 초 단위 기동, 문제가 생기면 버리고 재생성      |

#### 함께 필요한 기술

| 기술           | 역할                                    |
| ------------ | ------------------------------------- |
| 컨테이너 오케스트레이션 | 다수 컨테이너의 배치·확장·복구를 자동화(Kubernetes)    |
| 서비스 디스커버리    | 수시로 바뀌는 서비스의 위치(IP)를 찾아줌              |
| API 게이트웨이    | 외부 요청의 단일 진입점, 라우팅·인증                 |
| 서비스 메시       | 서비스 간 통신의 제어·암호화·관측(Istio 등)          |
| 중앙 로그·분산 추적  | 흩어진 로그와 요청 흐름을 한곳에서 확인                |

> [!note]+ 모든 시스템을 마이크로서비스로 만드는 것이 좋은가
>
> - 그렇지 않음
> - 규모가 작거나 팀이 작으면 서비스 분할로 얻는 이점보다 운용 복잡성이 더 큼
> - 처음에는 모놀리스로 빠르게 만들고, 규모와 조직이 커져 배포 충돌이나 확장 문제가 생기면 경계가 분명한 부분부터 서비스로 떼어내는 방식이 현실적

## 컨테이너와 서버리스의 비교: 실행 환경을 직접 묶어 가져가느냐, 사업자에게 맡기느냐.
### 서버리스란
- 서버리스(serverless): 개발자가 서버를 준비·관리하지 않고 코드만 올리면 실행되는 클라우드 이용 형태
- 서버가 없는 것이 아니라, 서버의 구축·확장·패치를 클라우드 사업자가 전담하여 이용자가 의식할 필요가 없는 것

| 종류                          | 내용                         | 예                                        |
| --------------------------- | -------------------------- | ---------------------------------------- |
| FaaS(Function as a Service) | 함수 단위의 코드를 이벤트가 발생할 때 실행   | AWS Lambda, Cloud Functions, Azure Functions |
| BaaS(Backend as a Service)  | 인증·DB·스토리지 등 백엔드 기능을 서비스로 제공 | Firebase, Amazon Cognito                 |

#### FaaS의 동작
1. 이벤트 발생
    - HTTP 요청, 파일 업로드, 메시지 도착, 정해진 시각
2. 사업자가 실행 환경을 준비
3. 함수 실행
4. 처리가 끝나면 실행 환경을 해제

- 이벤트 구동: 요청이 있을 때만 실행되고, 요청이 없으면 실행 환경도 없음
- 과금: `실행 횟수 × 실행 시간 × 메모리`
	- 실행되지 않으면 비용이 0

### 서버리스의 장단점

| 구분  | 내용                                   |
| --- | ------------------------------------ |
| 장점  | 서버 구축·패치·감시가 필요 없어 코드에 집중할 수 있음       |
| 장점  | 요청량에 따라 자동 확장(0까지 축소)                 |
| 장점  | 쓴 만큼만 과금되어 한가한 시간에는 비용이 없음            |
| 장점  | 빠른 개발·출시                             |
| 장점  | 고가용성을 사업자가 보장                         |
| 단점  | 콜드 스타트: 한동안 호출이 없다가 실행되면 환경 준비로 지연됨   |
| 단점  | 실행 시간·메모리·패키지 크기에 제한이 있음              |
| 단점  | 상태를 유지할 수 없어(stateless) 외부 저장소가 필요    |
| 단점  | 사업자 고유 방식에 묶임(벤더 종속)                  |
| 단점  | 로컬 테스트·디버깅·감시가 어려움                    |
| 단점  | 항상 높은 부하가 걸리면 오히려 비쌈                  |

> [!note]+ 콜드 스타트가 생기는 이유와 줄이는 방법
>
> - 서버리스는 요청이 없으면 실행 환경을 해제함
> - 다음 요청 때 환경을 새로 만들고 코드를 불러와야 해서 첫 응답이 늦어짐
> - 줄이는 방법
>     - 패키지 크기를 줄임
>     - 기동이 빠른 언어를 사용
>     - 실행 환경을 미리 준비해 두는 설정(프로비저닝)을 사용
> - 단, 미리 준비하면 그만큼 비용이 들어 '쓴 만큼만 과금'의 이점이 줄어듦

### 컨테이너와 서버리스의 차이

| 구분    | 컨테이너              | 서버리스(FaaS)          |
| ----- | ----------------- | ------------------- |
| 배포 단위 | 이미지(앱 + 실행 환경)    | 함수(코드)              |
| 실행 환경 | 이용자가 직접 정의, 자유도 높음 | 사업자가 제공, 지원 언어·버전 제한 |
| 실행 방식 | 상시 기동하여 요청 대기     | 이벤트가 있을 때만 기동       |
| 실행 시간 | 제한 없음             | 제한 있음(수 분~수십 분)     |
| 확장    | 설정 필요(오케스트레이션)    | 자동                  |
| 운용 부담 | 기반(클러스터·노드) 관리 필요 | 거의 없음               |
| 과금    | 기동 중인 자원에 대해      | 실행한 만큼              |
| 이식성   | 높음, 어디서나 실행       | 낮음, 사업자 종속          |
| 상태    | 유지 가능             | 유지 불가               |

#### 어울리는 용도

| 컨테이너                     | 서버리스                       |
| ------------------------ | -------------------------- |
| 상시 요청을 받는 웹·API 서비스      | 가끔 발생하는 이벤트 처리(파일 변환, 알림 발송) |
| 오래 걸리는 처리, 상태가 필요한 처리    | 짧게 끝나는 처리                  |
| 특수한 라이브러리·실행 환경이 필요한 경우  | 요청량 변동이 크거나 예측하기 어려운 경우     |
| 기존 애플리케이션 이전, 멀티 클라우드    | 소규모 팀의 빠른 개발, 정기 실행 작업      |

#### 서버리스 컨테이너
- 컨테이너와 서버리스의 접점
- 컨테이너 이미지를 올리면 기반 관리 없이 실행하고 자동으로 확장해 주는 서비스
	- AWS Fargate, Google Cloud Run, Azure Container Apps
- 컨테이너의 자유도·이식성에 서버리스의 운용 부담 경감을 더함
