## 도커: 사실상 컨테이너 기술의 표준
### 도커란
- 도커(Docker): 컨테이너형 가상화 기술로 애플리케이션을 빌드·배포·실행하는 오픈 소스 플랫폼
	- 컨테이너를 만들고 배포하고 실행하는 과정을 하나의 도구로 제공
- 2013년 dotCloud(현 Docker, Inc.)가 공개
- 애플리케이션과 실행에 필요한 라이브러리·설정을 컨테이너 이미지로 묶어 어디서나 같은 환경으로 실행
- 컨테이너 기술 자체는 이전부터 있었으나, 도커가 이미지 형식·배포 방법·간단한 명령어를 제공하면서 널리 퍼짐

| 용어       | 의미                              |
| -------- | ------------------------------- |
| 컨테이너 이미지 | 컨테이너 실행에 필요한 파일·설정을 담은 템플릿      |
| 컨테이너     | 이미지를 실행한 격리된 프로세스               |
| 도커 파일    | 이미지를 만드는 절차를 적은 텍스트 파일          |
| 레지스트리    | 이미지를 저장·공유하는 저장소(도커 허브 등)       |

### 도커의 장점

| 장점        | 내용                                       |
| --------- | ---------------------------------------- |
| 환경 통일     | 개발·테스트·운영을 같은 이미지로 구성해 '내 PC에서는 되는데' 문제를 해소 |
| 가볍고 빠름    | 게스트 OS가 없어 초 단위로 기동하고 자원 소비가 적음          |
| 이식성       | 도커가 동작하는 곳이면 온프레미스·클라우드 어디서나 실행         |
| 코드로 환경 관리 | 도커 파일로 환경 구축 절차를 기록해 재현·버전 관리 가능        |
| 이미지 공유    | 도커 허브의 공개 이미지를 내려받아 바로 사용               |
| 빠른 배포·롤백  | 이미지 교체로 배포하고, 이전 이미지로 되돌리기 쉬움           |

### 도커 엔진이란
- 도커 엔진: 컨테이너와 이미지를 생성·관리하는 핵심 소프트웨어
	- 클라이언트-서버 구조

| 구성 요소               | 역할                                        |
| ------------------- | ----------------------------------------- |
| 도커 데몬(dockerd)      | 호스트에 상주하며 이미지·컨테이너·네트워크·볼륨을 실제로 관리하는 서버 |
| REST API            | 데몬에 작업을 요청하는 인터페이스                        |
| 도커 클라이언트(docker CLI) | 사용자가 입력한 명령을 API로 데몬에 전달                 |

- 사용자 => docker 명령 => 도커 클라이언트 => REST API => 도커 데몬 => 컨테이너·이미지

#### 도커 엔진과 도커 데스크톱

| 구분    | 도커 엔진    | 도커 데스크톱                       |
| ----- | -------- | ----------------------------- |
| 대상 OS | 리눅스      | Windows, macOS, 리눅스           |
| 구성    | 데몬 + CLI | 도커 엔진 + GUI + 리눅스 가상 머신 + 쿠버네티스 등 |
| 용도    | 서버 운영 환경 | 개발자 PC                        |

> [!note]+ 도커는 가상 머신을 대체하는가
>
> - 대체가 아니라 가상화 단위가 다름
> - 가상 머신: 하드웨어를 가상화하여 OS 전체를 실행
> - 도커: 호스트 커널을 공유하며 프로세스 실행 환경만 격리
>     - 가볍고 빠르지만 호스트와 다른 종류의 커널은 쓸 수 없고 격리 수준이 상대적으로 낮음
> - 실제로는 클라우드 가상 서버 위에 도커를 올려 함께 쓰는 구성이 일반적

## 도커가 주목받는 이유: 사내 도구에서 컨테이너 표준의 토대가 되기까지
### 도커의 역사

| 연도   | 사건                                                    |
| ---- | ----------------------------------------------------- |
| 2008 | PaaS 사업자 dotCloud 설립, 자사 서비스 기반으로 컨테이너 기술을 사용          |
| 2013 | 사내 컨테이너 기술을 도커라는 이름의 오픈 소스로 공개, 회사명도 Docker, Inc.로 변경  |
| 2014 | 도커 1.0 출시, LXC 의존을 벗어나 자체 라이브러리(libcontainer)를 사용     |
| 2015 | OCI 설립, 도커가 컨테이너 런타임(runC)과 이미지 형식을 기증                |
| 2016 | 도커 엔진에 스웜 모드 내장, 클러스터 관리 기능 제공                        |
| 2017 | containerd를 CNCF에 기증, 도커 프로젝트의 오픈 소스 부분을 Moby로 분리     |
| 2019 | 도커 엔터프라이즈 사업을 Mirantis에 매각, 개발자 도구에 집중               |

### 도커의 주목도
- 공개 직후부터 개발자 커뮤니티에서 빠르게 확산됨
- AWS, 구글, 마이크로소프트 등 주요 클라우드 사업자가 도커 컨테이너를 실행하는 서비스를 잇달아 제공
- 도커 허브에 공개 이미지가 쌓이며 생태계가 형성됨
	- 이용자가 늘수록 편리해지는 구조
- 쿠버네티스 등 오케스트레이션 도구도 도커 이미지를 전제로 발전

### 도커가 주목받는 이유

| 이유          | 내용                                        |
| ----------- | ----------------------------------------- |
| 쉬운 사용법      | 네임스페이스·cgroups 같은 커널 기능을 `docker run` 한 줄로 사용 |
| 이미지라는 배포 단위 | 애플리케이션과 실행 환경을 하나로 묶어 그대로 전달              |
| 도커 파일       | 환경 구축 절차를 코드로 기록해 같은 이미지를 누구나 생성          |
| 도커 허브       | 이미지를 올리고 내려받는 공유의 장                       |
| 차분 관리(레이어)  | 바뀐 부분만 전송·저장하여 빠르게 배포                     |
| 시대적 요구      | 데브옵스·마이크로서비스·클라우드 확산과 맞물림                 |

#### 기존 컨테이너 기술(LXC 등)과 차이

| 구분    | 기존 컨테이너 기술            | 도커                |
| ----- | --------------------- | ----------------- |
| 초점    | 가벼운 가상 머신처럼 OS 환경을 격리 | 애플리케이션 단위의 패키징과 배포 |
| 환경 구성 | 수작업 설정                | 도커 파일로 자동화        |
| 공유    | 표준 방법 없음              | 이미지 + 레지스트리       |

### 컨테이너 기술의 발전을 지원하는 OCI
- OCI(Open Container Initiative): 컨테이너 업계 표준을 정하기 위해 2015년 리눅스 재단 산하에 설립된 단체
- 도커, CoreOS, 구글, 마이크로소프트, 레드햇 등이 참여
- 특정 기업의 기술에 종속되지 않도록 런타임과 이미지 형식을 표준화

| 표준                         | 내용                              |
| -------------------------- | ------------------------------- |
| 런타임 명세(runtime-spec)       | 컨테이너를 어떻게 실행할지 정의, 참조 구현은 runC   |
| 이미지 명세(image-spec)         | 컨테이너 이미지의 형식                    |
| 배포 명세(distribution-spec)   | 레지스트리와 이미지를 주고받는 방법              |

- 도커로 빌드한 이미지(OCI 형식)는 Podman, containerd, CRI-O 등 OCI를 따르는 어떤 런타임에서도 실행할 수 있음

> [!note]+ 도커가 핵심 기술을 OCI에 기증한 것이 중요한 이유
>
> - 표준이 없으면 도구마다 이미지 형식과 실행 방식이 달라 호환되지 않음
> - 도커가 runC와 이미지 형식을 기증하여 표준이 만들어짐
>     - 어떤 도구로 만든 이미지든 어떤 런타임에서든 실행할 수 있게 됨
> - 이용자는 특정 기업에 종속되지 않고, 다양한 컨테이너 기술이 같은 생태계에서 발전할 수 있었음

## 도커 컨테이너: 외부의 영향을 받지 않는 독립된 환경
### 컨테이너란
- 호스트 OS 위에서 다른 프로세스와 격리되어 실행되는 프로세스와 그 실행 환경
	- 호스트 커널을 공유하면서 프로세스·파일 시스템·네트워크를 격리
- 컨테이너 이미지를 실행하면 컨테이너가 됨
- 컨테이너 안에서는 자신만의 파일 시스템, 프로세스 목록, 네트워크를 가진 것처럼 보임
- 호스트에서 보면 컨테이너는 하나의 프로세스에 불과함

| 격리 대상    | 컨테이너 안에서 보이는 모습                |
| -------- | ------------------------------ |
| 프로세스     | 자기 컨테이너의 프로세스만 보임(PID 1부터 시작)  |
| 파일 시스템   | 이미지에 담긴 파일로 구성된 독자적인 루트 디렉터리   |
| 네트워크     | 독자적인 IP 주소와 포트                 |
| 호스트명·사용자 | 컨테이너별로 따로 가짐                   |

### 파일 시스템의 격리
- 컨테이너는 호스트의 파일 시스템이 아니라 이미지에 담긴 파일을 루트(`/`)로 사용
- 컨테이너 A에서 파일을 바꿔도 호스트나 컨테이너 B에는 영향이 없음
- 컨테이너의 실체는 호스트의 `/var/lib/docker` 아래에 존재
- 컨테이너마다 서로 다른 버전의 라이브러리를 가질 수 있어 의존성 충돌을 막음
- 호스트의 디렉터리를 컨테이너에 연결하려면 볼륨이나 바인드 마운트를 명시적으로 설정해야 함

### 컨테이너와 가상 서버의 차이

| 구분     | 가상 서버         | 컨테이너               |
| ------ | ------------- | ------------------ |
| 가상화 대상 | 하드웨어          | OS(프로세스 실행 환경)     |
| 게스트 OS | 가상 서버마다 필요    | 없음, 호스트 커널을 공유     |
| 크기     | GB 단위         | MB 단위              |
| 기동 시간  | 분 단위(OS 부팅)   | 초 단위(프로세스 시작)      |
| 자원 효율  | OS만큼 오버헤드가 있음 | 오버헤드가 작아 고밀도 배치 가능 |
| 격리 수준  | 강함            | 상대적으로 약함(커널 공유)    |
| OS 선택  | 자유            | 호스트 커널과 같은 계열만     |

> [!note]+ 컨테이너의 격리가 가상 서버보다 약하다고 하는 이유
>
> - 가상 서버는 각자 커널을 가짐
>     - 한 서버의 커널이 침해되어도 다른 서버에 직접 영향이 가기 어려움
> - 컨테이너는 모든 컨테이너가 호스트 커널 하나를 공유
>     - 커널 취약점이 악용되면 다른 컨테이너와 호스트까지 영향을 받을 수 있음
> - 컨테이너를 루트 권한 없이 실행하거나, 강한 격리가 필요하면 가상 서버 단위로 나누는 구성을 사용

### 어떻게 컨테이너에 운영 체제를 탑재할 수 있을까
- 컨테이너에는 게스트 OS가 없는데 ubuntu, centos, alpine 같은 이미지가 존재함

| OS의 구성                                     | 컨테이너에서                  |
| ------------------------------------------ | ----------------------- |
| 커널                                         | 호스트의 커널을 공유, 이미지에 들어 있지 않음 |
| 커널 이외(셸, 명령어, 라이브러리, 패키지 관리자 = 사용자 공간) | 이미지에 포함                 |

- ubuntu 이미지는 우분투에서 커널을 뺀 나머지 파일들
- 같은 리눅스 커널을 쓰므로 CentOS 호스트 위에서도 우분투 컨테이너가 동작
- 커널이 다른 OS는 실행할 수 없음
	- 리눅스 호스트에서 Windows 컨테이너는 실행 불가

### 컨테이너가 있다면 가상 서버는 필요 없을까

| 가상 서버가 적합한 경우               | 컨테이너가 적합한 경우            |
| --------------------------- | ----------------------- |
| 호스트와 다른 OS·커널이 필요           | 같은 커널 위에서 여러 애플리케이션을 실행 |
| 강한 격리가 필요(서로 다른 고객 환경 분리) | 빠른 기동·배포, 잦은 변경         |
| 커널 설정 변경, 커널 모듈 사용          | 높은 집적도, 자원 절약           |
| OS 전체를 관리해야 하는 기존 시스템       | 마이크로서비스, CI/CD          |

- 둘은 경쟁이 아니라 보완 관계
- 클라우드에서는 가상 서버 위에 컨테이너를 올려서 사용

## 컨테이너 이미지: 컨테이너를 실행하기 위한 템플릿
### 컨테이너 이미지란
- 컨테이너 실행에 필요한 파일 시스템과 설정 정보를 모아 둔 읽기 전용 템플릿
	- 애플리케이션과 실행 환경을 하나로 묶은 읽기 전용 파일 묶음

| 이미지에 담기는 것 | 예                    |
| ---------- | -------------------- |
| OS의 사용자 공간 | 셸, 기본 명령어, 라이브러리     |
| 미들웨어·런타임   | Nginx, JDK, Python   |
| 애플리케이션     | 소스 코드, 실행 파일         |
| 메타데이터      | 실행할 명령, 환경 변수, 공개할 포트 |

#### 이미지와 컨테이너의 관계

| 구분  | 이미지       | 컨테이너             |
| --- | --------- | ---------------- |
| 성격  | 템플릿(정적)   | 실행 중인 인스턴스(동적)   |
| 변경  | 읽기 전용     | 쓰기 가능한 레이어가 추가됨  |
| 비유  | 클래스, 붕어빵 틀 | 객체, 붕어빵          |

- 하나의 이미지로 여러 컨테이너를 만들 수 있음
- 이미지는 여러 레이어가 겹친 구조이며, 같은 레이어는 이미지끼리 공유

### 컨테이너 이미지의 생성

| 방법                        | 내용                              | 특징                   |
| ------------------------- | ------------------------------- | -------------------- |
| 도커 파일로 빌드(`docker build`)  | 절차를 적은 도커 파일을 읽어 자동 생성          | 권장, 재현 가능, 버전 관리 가능  |
| 컨테이너에서 생성(`docker commit`) | 실행 중인 컨테이너를 수정한 뒤 그 상태를 이미지로 저장 | 어떤 작업을 했는지 기록이 남지 않음 |

```dockerfile
FROM ubuntu:22.04                                 # 베이스 이미지
RUN apt-get update && apt-get install -y nginx    # 패키지 설치
COPY index.html /var/www/html/                    # 파일 복사
CMD ["nginx", "-g", "daemon off;"]                # 컨테이너 시작 시 실행할 명령
```

- 베이스 이미지: 새 이미지를 만들 때 토대가 되는 이미지
	- 그 위에 변경 사항을 레이어로 쌓음

> [!note]+ docker commit보다 도커 파일로 이미지를 만드는 것이 권장되는 이유
>
> - commit은 컨테이너 안에서 손으로 작업한 결과만 저장함
>     - 어떤 절차로 만들어졌는지 알 수 없고, 똑같이 다시 만들기도 어려움
> - 도커 파일은 생성 절차가 텍스트로 남음
>     - Git으로 변경 이력을 관리하고 코드 리뷰도 할 수 있음
> - CI 도구가 도커 파일을 읽어 자동으로 빌드할 수 있어 자동 빌드·배포와 잘 맞음

### 컨테이너 이미지의 배포
- 개발 PC(build) => push => 레지스트리 => pull => 운영 서버(run)

| 단계   | 명령             | 내용              |
| ---- | -------------- | --------------- |
| 빌드   | `docker build` | 도커 파일로 이미지 생성   |
| 업로드  | `docker push`  | 이미지를 레지스트리에 등록  |
| 다운로드 | `docker pull`  | 레지스트리에서 이미지 내려받기 |
| 실행   | `docker run`   | 이미지로 컨테이너 생성·시작 |

- 이미지 자체를 전달하므로 받는 쪽에서 환경을 다시 구축할 필요가 없음
- 이미 가진 레이어는 건너뛰고 없는 레이어만 전송

### 컨테이너 이미지는 운영 체제 설치 디스크와 같은 것일까

| 구분    | OS 설치 디스크(ISO)         | 컨테이너 이미지          |
| ----- | ---------------------- | ----------------- |
| 내용    | 커널을 포함한 OS 전체 + 설치 프로그램 | 커널을 제외한 파일 + 애플리케이션 |
| 사용 방법 | 설치 과정을 거쳐야 사용          | 설치 없이 바로 실행       |
| 결과물   | 범용 OS 환경               | 특정 애플리케이션을 위한 환경  |
| 크기    | GB 단위                  | 수 MB ~ 수백 MB      |
| 구조    | 하나의 덩어리                | 레이어의 겹침           |

- 설치 디스크는 OS를 설치하기 위한 재료, 컨테이너 이미지는 이미 구성이 끝난 실행 환경의 스냅숏
- 가상 서버의 머신 이미지(AMI 등)와 역할은 비슷하지만, 커널을 포함하지 않아 훨씬 가벼움

## 컨테이너의 라이프 사이클: 만들고 실행하고 멈추고 버리는 일회용 실행 환경
### 라이프 사이클이란
- 컨테이너가 생성되어 삭제될 때까지 거치는 상태의 흐름
- 컨테이너는 필요할 때 만들고, 필요 없으면 버리는 것이 기본 사고방식
- 문제가 생기면 고치지 않고 삭제한 뒤 이미지에서 다시 생성(불변 인프라)
- 남겨야 하는 데이터는 컨테이너 밖(볼륨)에 저장

| 상태             | 의미                               |
| -------------- | -------------------------------- |
| 생성(created)    | 컨테이너는 만들어졌지만 프로세스는 아직 시작되지 않음    |
| 실행(running)    | 컨테이너 안의 프로세스가 동작 중               |
| 일시 정지(paused)  | 프로세스가 일시 중단된 상태, 메모리 내용은 유지됨     |
| 정지(exited)     | 프로세스가 종료됨, 컨테이너 레이어의 파일은 남아 있음   |
| 삭제(removed)    | 컨테이너가 제거됨, 컨테이너 레이어의 변경 내용도 사라짐  |

### 컨테이너의 상태 변화
- 이미지 => 생성 => 실행 => (일시 정지) => 정지 => 삭제

| 명령                         | 상태 변화          | 내용                                |
| -------------------------- | -------------- | --------------------------------- |
| `docker create`            | 이미지 => 생성      | 컨테이너만 만들고 시작하지 않음                 |
| `docker start`             | 생성·정지 => 실행    | 컨테이너 시작                           |
| `docker run`               | 이미지 => 실행      | create + start를 한 번에              |
| `docker pause` / `unpause` | 실행 <=> 일시 정지   | 프로세스 일시 중단 / 재개                   |
| `docker stop`              | 실행 => 정지       | SIGTERM을 보내 정상 종료, 일정 시간 뒤 SIGKILL |
| `docker kill`              | 실행 => 정지       | SIGKILL로 즉시 강제 종료                 |
| `docker restart`           | 실행 => 정지 => 실행 | 재시작                               |
| `docker rm`                | 정지 => 삭제       | 컨테이너 삭제(`-f`를 붙이면 실행 중에도 삭제)      |

#### 정지와 삭제의 차이

| 구분            | 정지                    | 삭제     |
| ------------- | --------------------- | ------ |
| 프로세스          | 종료                    | 종료     |
| 컨테이너에서 변경한 파일 | 남아 있음, 다시 start하면 그대로 | 사라짐    |
| `docker ps`   | `-a` 옵션을 붙여야 보임       | 보이지 않음 |
| 디스크 사용        | 계속 차지                 | 반환     |

- 컨테이너의 수명은 메인 프로세스(PID 1)의 수명과 같음
	- 메인 프로세스가 끝나면 컨테이너도 정지
- `docker run --rm`: 정지와 동시에 자동 삭제
- `--restart` 옵션: 프로세스가 비정상 종료되거나 호스트가 재부팅되었을 때의 자동 재시작 정책을 지정

> [!note]+ 컨테이너를 삭제하면 이미지와 데이터는 어떻게 되는가
>
> - 컨테이너를 삭제해도 그 컨테이너를 만든 이미지는 남음
>     - 같은 이미지로 언제든 새 컨테이너를 만들 수 있음
> - 사라지는 것은 컨테이너가 실행 중에 기록한 변경 내용(컨테이너 레이어)
> - 데이터베이스 파일이나 업로드 파일처럼 남겨야 할 데이터는 볼륨에 저장해야 유지됨

## 도커 데몬: 도커 엔진을 지원하는 가장 중요한 요소
### 도커 엔진을 구성하는 세 구성 요소

| 구성 요소               | 역할                                     |
| ------------------- | -------------------------------------- |
| 도커 데몬(dockerd)      | 백그라운드에서 상주하는 서버, API 요청을 받아 도커 객체를 생성·관리 |
| 도커 API(REST API)    | 데몬에 작업을 지시하는 인터페이스                     |
| 도커 클라이언트(docker CLI) | 사용자의 명령을 API 요청으로 바꿔 데몬에 전달            |

- 도커 클라이언트 => (REST API) => 도커 데몬 => containerd => runC => 컨테이너
- 데몬은 pull/push로 레지스트리와 통신
- 데몬(daemon): 사용자와 직접 상호작용하지 않고 백그라운드에서 계속 동작하는 프로세스
- 실제 컨테이너 실행은 데몬이 containerd와 runC에 위임

### 도커 객체란
- 도커 데몬이 생성하고 관리하는 대상

| 객체   | 내용                               |
| ---- | -------------------------------- |
| 이미지  | 컨테이너를 만들기 위한 읽기 전용 템플릿           |
| 컨테이너 | 이미지를 실행한 인스턴스                    |
| 네트워크 | 컨테이너끼리, 또는 컨테이너와 외부가 통신하기 위한 가상 네트워크 |
| 볼륨   | 컨테이너의 데이터를 영속적으로 보관하는 저장 영역      |

- 스웜 모드에서는 서비스, 노드 등도 객체로 다룸
- 명령어도 객체 단위로 구성됨
	- `docker image ...`, `docker container ...`, `docker network ...`, `docker volume ...`

### 도커 데몬과 통신

| 통신 방법  | 내용                              | 용도                |
| ------ | ------------------------------- | ----------------- |
| 유닉스 소켓 | `/var/run/docker.sock` 파일을 통한 통신 | 같은 호스트의 클라이언트(기본값) |
| TCP 소켓 | 네트워크를 통한 통신(2375 평문, 2376 TLS)  | 원격 호스트의 데몬 조작     |

- 클라이언트와 데몬이 같은 호스트에 없어도 됨
	- PC의 docker 명령으로 원격 서버의 컨테이너를 조작할 수 있음
- docker CLI뿐 아니라 API를 쓰는 프로그램(SDK, 도커 컴포즈, CI 도구)도 데몬과 통신할 수 있음

> [!note]+ 도커 소켓을 컨테이너에 마운트하면 위험한 이유
>
> - 소켓(`/var/run/docker.sock`)에 접근할 수 있다는 것은 데몬에 어떤 명령이든 내릴 수 있다는 뜻
> - 데몬은 보통 root 권한으로 동작함
>     - 소켓을 가진 컨테이너는 호스트 디렉터리를 마운트한 새 컨테이너를 띄우는 식으로 호스트 전체를 장악할 수 있음
> - TCP로 데몬을 공개할 때 TLS 인증 없이 여는 것도 같은 이유로 위험

### 여러 구성 요소로 나누어져 있을 때의 장점

| 장점         | 내용                                         |
| ---------- | ------------------------------------------ |
| 원격 조작      | 클라이언트만 설치하면 다른 호스트의 데몬을 조작할 수 있음           |
| 다양한 클라이언트  | API만 맞으면 CLI, GUI, 자동화 도구 등 무엇이든 사용 가능      |
| 독립적인 교체·갱신 | 구성 요소별로 개선·교체가 쉬움(런타임을 containerd·runC로 분리) |
| 재사용        | 분리된 containerd는 도커 없이 쿠버네티스에서도 사용           |
| 안정성        | 데몬을 재시작해도 실행 중인 컨테이너를 유지하도록 구성 가능(live restore) |

## 컨테이너와 프로세스: 프로세스별로 컨테이너를 나눈다.
### 하나의 컨테이너에 하나의 프로세스가 기준
- 컨테이너는 메인 프로세스(PID 1)가 실행되는 동안만 살아 있음
- 웹 서버, 애플리케이션, 데이터베이스를 한 컨테이너에 몰아넣지 않고 역할별로 분리
	- 나쁜 예: 컨테이너 1개에 웹 서버 + 애플리케이션 + DB
	- 좋은 예: 컨테이너 A는 웹 서버(Nginx), 컨테이너 B는 애플리케이션, 컨테이너 C는 DB(MySQL)
	- 컨테이너끼리는 네트워크로 통신
- '프로세스 1개'는 엄밀한 규칙이라기보다 '하나의 컨테이너 = 하나의 관심사'라는 원칙
	- 웹 서버가 워커 프로세스를 여러 개 띄우는 것은 문제없음

### 프로세스별로 컨테이너를 나눌 때 장점

| 장점      | 내용                                  |
| ------- | ----------------------------------- |
| 독립적인 갱신 | 애플리케이션만 바꿀 때 DB 컨테이너는 그대로 둠         |
| 독립적인 확장 | 부하가 걸리는 컨테이너만 수를 늘림                 |
| 장애 격리   | 한 프로세스의 문제가 다른 컨테이너로 번지지 않음         |
| 재사용     | 공식 이미지(nginx, mysql 등)를 그대로 조합하여 사용 |
| 관리 단순화  | 컨테이너 상태 = 프로세스 상태, 감시·재시작·로그 수집이 명확 |
| 이미지 경량화 | 필요한 것만 담아 크기가 작고 취약점도 줄어듦          |

### 프로세스별로 컨테이너를 나눌 때 단점

| 단점           | 내용                       |
| ------------ | ------------------------ |
| 컨테이너 수 증가    | 관리 대상이 늘어 구성이 복잡해짐       |
| 컨테이너 간 연결 필요 | 네트워크, 기동 순서, 의존 관계를 따로 설정 |
| 장애 원인 추적     | 여러 컨테이너에 걸친 로그를 모아서 봐야 함  |
| 통신 오버헤드      | 같은 호스트 안에서도 네트워크를 거쳐 통신   |

- 해결 수단
	- 도커 컴포즈(Docker Compose): 여러 컨테이너를 한 파일로 정의
	- 오케스트레이션 도구(스웜 모드, 쿠버네티스): 다수 호스트의 컨테이너를 관리

### 볼륨이란
- 볼륨(volume): 컨테이너의 데이터를 컨테이너 밖(호스트)에 보관하는 저장 영역
	- 컨테이너를 삭제해도 데이터가 남음
- 컨테이너에서 쓴 데이터는 컨테이너 레이어에 기록되므로, 컨테이너를 삭제하면 함께 사라짐
- 볼륨을 컨테이너의 디렉터리에 마운트하면 그 경로의 데이터는 호스트에 저장됨
- 여러 컨테이너가 같은 볼륨을 마운트하여 데이터를 공유할 수도 있음

| 종류       | 저장 위치                                  | 특징                        | 용도                        |
| -------- | -------------------------------------- | ------------------------- | ------------------------- |
| 볼륨       | 도커가 관리하는 영역(`/var/lib/docker/volumes`) | 도커 명령으로 관리, 호스트 경로에 의존하지 않음 | DB 데이터 등 영속 데이터(권장)       |
| 바인드 마운트  | 사용자가 지정한 호스트 경로                        | 호스트의 파일을 그대로 공유            | 개발 중 소스 코드 공유, 설정 파일 전달   |
| tmpfs 마운트 | 호스트의 메모리                               | 컨테이너가 멈추면 사라짐              | 임시 데이터, 디스크에 남기면 안 되는 정보 |

```bash
docker volume create db-data                                  # 볼륨 생성
docker run -d -v db-data:/var/lib/mysql mysql                 # 볼륨을 컨테이너 경로에 마운트
docker run -d -v $(pwd)/html:/usr/share/nginx/html nginx      # 바인드 마운트
```

> [!note]+ DB 컨테이너를 새 버전 이미지로 교체하면 데이터는 어떻게 되는가
>
> - 데이터 디렉터리를 볼륨에 두었다면 데이터가 이어짐
>     - 기존 컨테이너를 삭제하고, 새 이미지로 만든 컨테이너에 같은 볼륨을 마운트
> - 볼륨 없이 컨테이너 레이어에만 저장했다면 컨테이너 삭제와 함께 데이터도 사라짐
> - 컨테이너(실행 환경)와 데이터(상태)를 분리해야 컨테이너를 일회용으로 다룰 수 있음

## 네임스페이스: 작업 공간을 분리하는 방법
### 네임스페이스란
- 네임스페이스(namespace): 프로세스가 볼 수 있는 시스템 자원의 범위를 나누어, 프로세스마다 독립된 공간이 있는 것처럼 보이게 하는 리눅스 커널 기능
- 같은 네임스페이스에 속한 프로세스끼리만 서로의 자원이 보임
- 다른 네임스페이스의 프로세스, 네트워크, 파일은 존재하지 않는 것처럼 보임
- 하드웨어를 가상화하지 않고도 격리된 환경을 만들 수 있는 이유
- 네임스페이스로 '보이는 범위'를 나누고, 컨트롤 그룹으로 '쓸 수 있는 양'을 제한

### 네임스페이스와 컨테이너
- 컨테이너 = 네임스페이스로 격리된 프로세스 + 컨트롤 그룹으로 자원 제한
- 도커는 컨테이너를 만들 때마다 그 컨테이너 전용 네임스페이스 묶음을 만듦
	- PID NS, NET NS, MNT NS, UTS NS 등
- 컨테이너 A 안에서 `ps`를 실행하면 A의 프로세스만 보이고 PID도 1부터 시작
- 호스트에서 보면 컨테이너 A와 B의 프로세스는 모두 일반 프로세스로 보임
	- 서로 다른 PID를 가짐

### 네임스페이스에 의해 격리된 리소스

| 네임스페이스       | 격리 대상                              | 효과                          |
| ------------ | ---------------------------------- | --------------------------- |
| PID          | 프로세스 ID                            | 컨테이너별로 독립된 프로세스 번호 체계       |
| Network(NET) | 네트워크 인터페이스, IP 주소, 포트, 라우팅 테이블     | 컨테이너마다 독자 IP, 같은 포트 번호 사용 가능 |
| Mount(MNT)   | 파일 시스템의 마운트 지점                     | 컨테이너별로 독립된 디렉터리 구조          |
| UTS          | 호스트명, 도메인명                         | 컨테이너별 호스트명                  |
| IPC          | 프로세스 간 통신 자원(공유 메모리, 세마포어, 메시지 큐) | 다른 컨테이너의 IPC에 접근 불가         |
| User         | 사용자 ID, 그룹 ID                      | 컨테이너 안의 root를 호스트의 일반 사용자로 대응 |
| Cgroup       | 컨트롤 그룹의 계층 정보                      | 컨테이너에서 호스트의 cgroup 구조가 보이지 않음 |

### 컨트롤 그룹이란
- 컨트롤 그룹(cgroups, control groups): 프로세스를 그룹으로 묶어 그 그룹이 쓸 수 있는 자원의 양을 제한하고 감시하는 리눅스 커널 기능

| 구분  | 네임스페이스                | 컨트롤 그룹               |
| --- | --------------------- | -------------------- |
| 역할  | 무엇이 보이는지 격리           | 얼마나 쓸 수 있는지 제한       |
| 없으면 | 다른 컨테이너의 프로세스와 파일이 보임 | 한 컨테이너가 호스트의 자원을 독점  |

#### 제어 대상

| 제어 대상  | 내용                               |
| ------ | -------------------------------- |
| CPU    | 사용 시간의 비율과 상한                    |
| 메모리    | 사용량 상한, 넘으면 프로세스 강제 종료(OOM Kill) |
| 블록 I/O | 디스크 읽기·쓰기 속도                     |
| PID 수  | 생성할 수 있는 프로세스 수                  |
| 장치     | 접근 가능한 장치                        |

```bash
docker run -d --cpus=1.5 --memory=512m nginx    # CPU 1.5개, 메모리 512MB로 제한
```

> [!note]+ 네임스페이스만 있고 컨트롤 그룹이 없다면
>
> - 네임스페이스는 보이는 범위만 나누고 사용량은 제한하지 않음
> - 한 컨테이너에서 메모리 누수나 무한 루프가 생기면 호스트의 CPU와 메모리를 모두 차지함
>     - 같은 호스트의 다른 컨테이너까지 느려지거나 멈춤
> - 컨트롤 그룹으로 컨테이너별 상한을 정하면 문제의 영향을 그 컨테이너 안으로 한정할 수 있음

### 컨트롤 그룹의 계층 구조
- 컨트롤 그룹은 트리(계층) 구조
- 가상 파일 시스템 `/sys/fs/cgroup`을 통해 조작
- 하위 그룹은 상위 그룹의 제한을 상속하며, 상위 그룹의 한도를 넘을 수 없음
- 계층 예시
	- `/sys/fs/cgroup`: 루트, 시스템 전체
		- `system.slice`: 시스템 서비스
			- `docker-<컨테이너 A ID>.scope`: 메모리 512MB
			- `docker-<컨테이너 B ID>.scope`: 메모리 1GB
		- `user.slice`: 사용자 세션

| 구분  | cgroup v1                     | cgroup v2       |
| --- | ----------------------------- | --------------- |
| 구조  | 자원 종류(CPU, 메모리 등)별로 계층이 따로 존재 | 단일 계층으로 통합      |
| 관리  | 복잡                            | 단순하고 일관됨        |
| 채택  | 과거 기본값                        | 최근 리눅스 배포판의 기본값 |

## 차분 관리: 도커의 빠른 배포를 지원하는 방법
### 차분 관리란
- 전체를 매번 복사하지 않고 이전 상태와 달라진 부분(차분)만 기록·관리하는 방식
- 컨테이너 이미지는 여러 레이어가 겹쳐진 구조
	- 각 레이어는 바로 아래 레이어와의 차이만 가짐
- 유니온 파일 시스템(OverlayFS 등)이 여러 레이어를 겹쳐 하나의 파일 시스템처럼 보이게 함
- 도커 파일의 명령(FROM, RUN, COPY 등)마다 레이어가 하나씩 생성됨

### 이미지 레이어의 특징

| 특징     | 내용                                   |
| ------ | ------------------------------------ |
| 읽기 전용  | 한 번 만들어진 레이어는 변경되지 않음                |
| 차분만 보유 | 아래 레이어에서 추가·변경·삭제된 파일만 기록            |
| 공유     | 같은 레이어는 여러 이미지가 함께 사용, 디스크에 한 번만 저장  |
| 식별     | 내용의 해시값(다이제스트)으로 구분, 같은 내용이면 같은 레이어  |
| 캐시     | 빌드 시 변경이 없는 레이어는 다시 만들지 않고 재사용       |

- 레이어 공유 예시
	- 이미지 A: ubuntu => python 설치 => 앱 A 복사
	- 이미지 B: ubuntu => python 설치 => 앱 B 복사
	- ubuntu와 python 설치 레이어는 공유하고, 앱 레이어만 따로 저장

### 컨테이너 레이어의 특징
- 컨테이너 레이어: 컨테이너를 만들 때 이미지 레이어 맨 위에 추가되는 쓰기 가능한 레이어

| 특징       | 내용                                         |
| -------- | ------------------------------------------ |
| 읽기·쓰기 가능 | 컨테이너에서 일어난 파일 생성·변경·삭제가 여기에 기록됨            |
| 컨테이너마다 하나 | 같은 이미지로 만든 컨테이너들은 이미지 레이어를 공유하고 컨테이너 레이어만 각자 가짐 |
| 일시적      | 컨테이너를 삭제하면 함께 사라짐                          |
| 얇음       | 변경분만 담으므로 컨테이너 생성 시 이미지를 복사하지 않아 순식간에 기동됨   |

#### 쓰기 시 복사(Copy-on-Write)

| 동작  | 처리                                          |
| --- | ------------------------------------------- |
| 읽기  | 위 레이어부터 아래로 찾아 내려가 처음 발견한 파일을 읽음            |
| 수정  | 이미지 레이어의 파일을 컨테이너 레이어로 복사한 뒤 수정, 원본은 그대로 둠  |
| 삭제  | 컨테이너 레이어에 '삭제됨' 표시(화이트아웃)만 기록, 아래 레이어의 파일은 남아 있음 |

### 차분 관리의 장단점

| 구분  | 내용                                     |
| --- | -------------------------------------- |
| 장점  | 같은 레이어를 공유하여 디스크를 절약                   |
| 장점  | 없는 레이어만 push/pull하여 전송 시간을 단축          |
| 장점  | 변경된 레이어부터만 다시 빌드하여 빌드 시간을 단축           |
| 장점  | 이미지를 복사하지 않아 컨테이너 기동이 빠름               |
| 단점  | 레이어가 많아지면 파일 탐색에 오버헤드가 생김              |
| 단점  | 쓰기 시 복사 때문에 쓰기가 많은 처리는 느림(볼륨 사용 권장)    |
| 단점  | 아래 레이어에서 지운 파일도 용량은 그대로 차지             |
| 단점  | 한번 레이어에 들어간 비밀 정보는 뒤에서 지워도 남음         |

#### 레이어를 고려한 도커 파일 작성
- 자주 바뀌는 것은 뒤쪽에 둠
	- 의존 라이브러리 설치를 먼저, 소스 코드 복사를 나중에 하여 캐시를 활용
- 설치와 정리를 하나의 RUN으로 묶어 불필요한 파일이 레이어에 남지 않게 함
- 멀티 스테이지 빌드로 빌드 도구는 버리고 결과물만 최종 이미지에 포함

> [!note]+ 소스 코드를 한 줄 고쳤는데 이미지 빌드와 배포가 금방 끝나는 이유
>
> - 도커는 도커 파일의 각 명령을 레이어로 캐시해 두고, 변경이 생긴 명령부터만 다시 실행함
> - 베이스 이미지와 라이브러리 설치 레이어는 재사용되고, 소스 코드를 복사하는 레이어만 새로 만들어짐
> - 배포할 때도 레지스트리와 서버에 이미 있는 레이어는 건너뛰고 바뀐 레이어만 전송함

## 스웜 모드: 클러스터를 관리하는 기능
### 스웜 모드란
- 스웜 모드(Swarm mode): 여러 도커 호스트를 하나의 클러스터(스웜)로 묶어 관리하는 도커 엔진의 내장 기능
	- 컨테이너를 배치, 복구, 확장하는 도커 내장 오케스트레이션
- 클러스터: 여러 대의 서버를 묶어 하나의 시스템처럼 동작하게 만든 것
- 호스트 한 대로는 장애에 취약하고 처리 능력에도 한계가 있으므로, 컨테이너를 여러 호스트에 분산
- 별도의 소프트웨어 설치 없이 `docker swarm init` 명령으로 시작
	- 도커 1.12부터 내장

| 기능        | 내용                                  |
| --------- | ----------------------------------- |
| 클러스터 관리   | 노드의 참가, 이탈, 상태 관리                   |
| 원하는 상태 유지 | 지정한 수의 컨테이너가 항상 실행되도록 자동 복구         |
| 스케일링      | 컨테이너 수를 명령 하나로 늘리거나 줄임              |
| 로드 밸런싱    | 어느 노드로 요청이 와도 서비스의 컨테이너로 분산(라우팅 메시) |
| 롤링 업데이트   | 컨테이너를 순차적으로 새 버전으로 교체               |
| 서비스 디스커버리 | 서비스 이름으로 컨테이너에 접근(내장 DNS)           |

### 매니저와 워커
- 노드(node): 스웜에 참가한 도커 호스트
	- 역할에 따라 매니저와 워커로 나뉨

| 구분      | 매니저 노드                                  | 워커 노드                  |
| ------- | --------------------------------------- | ---------------------- |
| 역할      | 클러스터 상태 관리, 태스크 배치(스케줄링), 명령 접수         | 매니저가 할당한 태스크(컨테이너) 실행  |
| 명령 실행   | `docker service` 등 관리 명령 가능             | 불가                     |
| 컨테이너 실행 | 기본적으로 가능(제외하도록 설정 가능)                   | 가능                     |
| 장애 대비   | Raft 합의 알고리즘으로 상태를 복제, 홀수 대(3대, 5대) 구성 권장 | 장애 시 다른 노드에서 태스크를 재실행  |

- 매니저가 N대일 때 `(N-1)/2`대까지의 장애를 견딤
	- 3대면 1대, 5대면 2대까지

### 서비스와 태스크

| 용어           | 의미                                      |
| ------------ | --------------------------------------- |
| 서비스(service) | '어떤 이미지를 몇 개 실행할지'를 정의한 원하는 상태, 사용자가 다루는 단위 |
| 태스크(task)    | 서비스를 이루는 실행 단위, 컨테이너 1개에 대응하며 스웜이 노드에 배치  |

| 서비스 종류             | 내용                                   |
| ------------------ | ------------------------------------ |
| 복제 서비스(replicated) | 지정한 개수의 태스크를 클러스터에 분산 배치             |
| 글로벌 서비스(global)    | 모든 노드에 태스크를 하나씩 배치(감시 에이전트, 로그 수집기 등) |

```bash
docker swarm init                                              # 스웜 초기화 (현재 노드가 매니저)
docker swarm join --token <토큰> <매니저 IP>:2377               # 다른 호스트를 스웜에 참가
docker service create --name web --replicas 3 -p 80:80 nginx   # 서비스 생성
docker service scale web=5                                     # 태스크 수 변경
docker service update --image nginx:1.27 web                   # 롤링 업데이트
```

- 태스크가 실행되던 노드가 멈추면 매니저가 다른 노드에 새 태스크를 만들어 개수를 유지

### 클러스터를 관리하는 도구

| 도구                     | 개발              | 특징                                |
| ---------------------- | --------------- | --------------------------------- |
| 도커 스웜 모드               | Docker          | 도커에 내장, 구성이 간단하고 도커 명령과 유사, 소규모에 적합 |
| 쿠버네티스                  | 구글에서 시작, 이후 CNCF | 기능이 풍부하고 생태계가 큼, 사실상 표준            |
| Apache Mesos(Marathon) | Apache          | 컨테이너 이외의 작업도 다루는 범용 클러스터 관리        |
| Nomad                  | HashiCorp       | 단순하고 가벼우며 컨테이너 이외의 작업도 실행          |
| 아마존 ECS                | AWS             | AWS 전용 관리형 오케스트레이션 서비스             |

> [!note]+ 도커에 스웜 모드가 내장되어 있는데 쿠버네티스가 더 널리 쓰이는 이유
>
> - 스웜 모드는 배우기 쉽고 구성이 간단함
> - 자동 스케일링, 세밀한 배포 제어, 확장 기능은 쿠버네티스가 훨씬 풍부함
> - 주요 클라우드 사업자가 모두 관리형 쿠버네티스를 제공하고, 주변 도구 생태계도 쿠버네티스 중심
> - 소규모·단순한 구성에는 스웜 모드, 대규모·복잡한 운영에는 쿠버네티스를 선택하는 경우가 많음

## 도커의 주요 명령어: 컨테이너와 이미지를 다루는 기본 명령과 도커 파일
### 도커 명령어를 사용할 수 있는 환경

| 환경              | 내용                                    |
| --------------- | ------------------------------------- |
| 리눅스             | 도커 엔진을 직접 설치, 서버 운영 환경의 기본             |
| Windows / macOS | 도커 데스크톱 설치, 내부의 리눅스 가상 머신에서 도커 엔진 실행   |
| 클라우드            | 가상 서버에 도커를 설치하거나, 브라우저에서 쓰는 클라우드 셸 사용  |
| 온라인 실습 환경       | Play with Docker, 설치 없이 브라우저에서 실습      |

```bash
docker version     # 클라이언트와 서버(데몬)의 버전 확인
docker info        # 도커 환경 정보 (컨테이너·이미지 수, 스토리지 드라이버 등)
```

### 도커 명령어의 기본
- 형식: `docker [대상] [동작] [옵션] [인수]`
	- 예: `docker container run -d -p 8080:80 nginx`
	- 대상은 `container`, 동작은 `run`, 옵션은 `-d -p 8080:80`, 인수(이미지)는 `nginx`
- 대상: `container`, `image`, `network`, `volume` 등 도커 객체 단위
- 기존의 짧은 명령도 그대로 쓸 수 있음
	- `docker container run`은 `docker run`과 같음
- `docker --help`, `docker run --help`로 사용법을 확인

### 컨테이너의 시작/분리/표시/정지/삭제

| 작업  | 명령                                  | 내용                                  |
| --- | ----------------------------------- | ----------------------------------- |
| 시작  | `docker run [옵션] 이미지`               | 컨테이너를 생성하고 시작, 이미지가 없으면 자동으로 pull    |
| 분리  | `docker run -d` / `Ctrl+P, Ctrl+Q`  | 백그라운드 실행 / 접속한 컨테이너에서 빠져나옴(컨테이너는 계속 실행) |
| 표시  | `docker ps`                         | 실행 중인 컨테이너 목록(`-a`: 정지된 것 포함)        |
| 접속  | `docker exec -it 컨테이너 bash`         | 실행 중인 컨테이너에서 명령 실행                   |
| 로그  | `docker logs 컨테이너`                  | 컨테이너 출력 확인(`-f`: 계속 따라가기)            |
| 정지  | `docker stop 컨테이너`                  | 컨테이너 정지                             |
| 삭제  | `docker rm 컨테이너`                    | 정지된 컨테이너 삭제(`-f`: 실행 중이어도 삭제)        |

#### run의 주요 옵션

| 옵션               | 의미                |
| ---------------- | ----------------- |
| `-d`             | 백그라운드(분리 모드)로 실행  |
| `-it`            | 터미널을 연결해 대화형으로 실행 |
| `--name 이름`      | 컨테이너 이름 지정        |
| `-p 호스트포트:컨테이너포트` | 포트 공개             |
| `-v 볼륨:경로`       | 볼륨 마운트            |
| `-e 변수=값`        | 환경 변수 설정          |
| `--rm`           | 정지 시 자동 삭제        |

```bash
docker run -d --name web -p 8080:80 nginx    # 시작
docker ps                                    # 표시
docker stop web                              # 정지
docker rm web                                # 삭제
```

### 컨테이너 이미지의 생성/표시/삭제

| 작업     | 명령                        | 내용                              |
| ------ | ------------------------- | ------------------------------- |
| 내려받기   | `docker pull 이미지:태그`      | 레지스트리에서 이미지 다운로드                |
| 생성     | `docker commit 컨테이너 이미지:태그` | 컨테이너의 현재 상태를 이미지로 저장            |
| 생성     | `docker build -t 이미지:태그 .` | 도커 파일로 이미지 빌드                   |
| 표시     | `docker images`           | 로컬에 있는 이미지 목록                   |
| 이력     | `docker history 이미지`      | 이미지를 구성하는 레이어 확인                |
| 이름 붙이기 | `docker tag 원본 새이름:태그`    | 이미지에 다른 이름과 태그 부여               |
| 올리기    | `docker push 이미지:태그`      | 레지스트리에 이미지 업로드                  |
| 삭제     | `docker rmi 이미지`          | 이미지 삭제, 그 이미지로 만든 컨테이너가 있으면 불가  |

### 도커 파일로 컨테이너 이미지 생성
- 도커 파일(Dockerfile): 이미지를 만드는 절차를 순서대로 적은 텍스트 파일

| 명령                   | 역할                      |
| -------------------- | ----------------------- |
| `FROM`               | 베이스 이미지 지정              |
| `WORKDIR`            | 작업 디렉터리 지정              |
| `COPY` / `ADD`       | 호스트의 파일을 이미지로 복사        |
| `RUN`                | 빌드 시 실행할 명령(패키지 설치 등)   |
| `ENV`                | 환경 변수 설정                |
| `EXPOSE`             | 컨테이너가 사용하는 포트 명시        |
| `CMD` / `ENTRYPOINT` | 컨테이너 시작 시 실행할 명령        |

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["python", "app.py"]
```

```bash
docker build -t myapp:1.0 .            # 현재 디렉터리의 Dockerfile로 빌드
docker run -d -p 8000:8000 myapp:1.0   # 만든 이미지로 컨테이너 실행
```

> [!note]+ RUN과 CMD의 차이
>
> - RUN: 이미지를 빌드할 때 실행되고 결과가 이미지의 레이어로 저장됨
>     - 패키지 설치처럼 환경을 만드는 작업에 사용
> - CMD: 빌드 때는 실행되지 않고, 그 이미지로 컨테이너를 시작할 때 실행할 기본 명령을 지정
> - RUN은 '이미지에 무엇을 넣을지', CMD는 '컨테이너가 무엇을 할지'를 정함

### 도커 명령어를 사용하는 곳

| 장면          | 사용 예                                      |
| ----------- | ----------------------------------------- |
| 개발 PC       | DB나 캐시 등 개발 환경을 컨테이너로 준비, 이미지 빌드와 동작 확인   |
| CI/CD 파이프라인 | 코드가 올라오면 자동으로 build, 테스트, push            |
| 운영 서버       | 이미지를 pull하여 컨테이너 실행, 로그와 상태 확인           |
| 장애 조사       | `logs`, `exec`, `inspect`, `stats`로 원인 파악 |

- 여러 컨테이너를 함께 다룰 때는 도커 컴포즈(`docker compose up`)로 정의 파일 하나에 묶어 실행
- 쿠버네티스를 쓰는 운영 환경에서는 컨테이너 조작을 kubectl이 맡고, docker 명령은 주로 이미지 빌드에 사용

## 도커 허브: 컨테이너 이미지를 공유하는 서비스
### 도커 허브란
- 도커 허브(Docker Hub): 도커사가 운영하는 클라우드형 컨테이너 레지스트리 서비스
	- 세계 최대의 컨테이너 레지스트리
- `docker pull nginx`처럼 레지스트리를 지정하지 않으면 기본으로 도커 허브에서 내려받음
- 계정을 만들면 자신의 이미지를 공개하거나 비공개로 보관할 수 있음

| 이미지 종류                      | 내용                                           |
| --------------------------- | -------------------------------------------- |
| 도커 공식 이미지(Official Image)   | 도커가 검증·관리하는 이미지, `nginx`, `ubuntu`, `mysql`처럼 사용자명이 없음 |
| 검증된 게시자(Verified Publisher) | 소프트웨어 제공 기업이 직접 배포하는 이미지                      |
| 일반 사용자 이미지                  | 누구나 올린 이미지, `사용자명/이미지명` 형태이며 신뢰성은 직접 확인해야 함   |

| 기능            | 내용                                  |
| ------------- | ----------------------------------- |
| 이미지 검색과 공유    | 공개된 이미지를 찾아 바로 사용                    |
| 공개/비공개 리포지터리 | 공개 범위 설정, 무료 계정은 비공개 리포지터리 수에 제한이 있음 |
| 자동 빌드         | GitHub 등의 소스가 바뀌면 이미지를 자동 생성(유료)     |
| 취약점 스캔        | 이미지에 포함된 알려진 취약점 검사                  |
| 웹훅            | 이미지가 올라오면 다른 서비스에 알림을 보내 배포를 자동화     |

### 컨테이너 레지스트리란
- 컨테이너 이미지를 저장하고 배포하는 서버(서비스)
- 개발자 => `docker push` => 레지스트리 => `docker pull` => 운영 서버, 다른 개발자, CI 도구

| 구분    | 퍼블릭 레지스트리         | 프라이빗 레지스트리            |
| ----- | ----------------- | --------------------- |
| 공개 범위 | 누구나 접근            | 인증된 사용자만 접근           |
| 용도    | 오픈 소스와 공식 이미지 배포  | 사내 애플리케이션 이미지 보관      |
| 예     | 도커 허브             | 클라우드의 레지스트리 서비스, 자체 구축 |

- 레지스트리가 없으면 이미지를 파일로 저장(`docker save`)하여 직접 옮겨야 함
	- 그래서 레지스트리가 배포의 중심이 됨

### 리포지터리와 태그

| 용어    | 의미                             |
| ----- | ------------------------------ |
| 레지스트리 | 리포지터리들을 모아 둔 서버                |
| 리포지터리 | 같은 이름의 이미지를 버전별로 모아 둔 곳        |
| 태그    | 리포지터리 안에서 이미지를 구분하는 이름, 주로 버전  |

- 이미지 이름의 구조: `docker.io/library/nginx:1.27`
	- `docker.io`: 레지스트리
	- `library`: 네임스페이스
	- `nginx`: 리포지터리
	- `1.27`: 태그
- `docker pull nginx`는 `docker.io/library/nginx:latest`와 같음
- 태그를 생략하면 `latest`로 간주됨
	- 가장 최신이라는 보장이 아니라 기본 태그 이름일 뿐
- 같은 태그에 다른 이미지를 덮어쓸 수 있으므로, 운영 환경에서는 `latest` 대신 명확한 버전 태그를 사용
- 내용까지 고정하려면 다이제스트(`nginx@sha256:...`)로 지정

```bash
docker tag myapp:1.0 myuser/myapp:1.0    # 리포지터리 이름에 맞춰 태그 부여
docker login                             # 도커 허브 로그인
docker push myuser/myapp:1.0             # 업로드
```

### 도커 허브 이외의 컨테이너 레지스트리 서비스

| 서비스                                    | 제공              | 특징                          |
| -------------------------------------- | --------------- | --------------------------- |
| Amazon ECR                             | AWS             | ECS, EKS와 연동, IAM으로 접근 제어    |
| Artifact Registry(구 Container Registry) | Google Cloud    | GKE, Cloud Run과 연동          |
| Azure Container Registry(ACR)          | Microsoft Azure | AKS, ACI와 연동                |
| GitHub Container Registry(ghcr.io)     | GitHub          | 소스 저장소, GitHub Actions와 연동  |
| Quay.io                                | Red Hat         | 취약점 스캔, OpenShift와 연동       |
| Harbor                                 | CNCF(오픈 소스)     | 자체 서버에 구축하는 프라이빗 레지스트리      |

- 클라우드에서 컨테이너를 실행할 때는 같은 클라우드의 레지스트리를 쓰면 전송이 빠르고 권한 관리가 쉬움

> [!note]+ 도커 허브의 이미지를 그대로 운영 환경에 써도 되는가
>
> - 공식 이미지나 검증된 게시자의 이미지는 비교적 안전함
> - 일반 사용자가 올린 이미지에는 취약한 패키지나 악성 코드가 들어 있을 수 있음
> - 출처와 갱신 여부를 확인하고, 태그를 버전이나 다이제스트로 고정하고, 취약점 스캔을 거친 뒤 사용
> - 도커 허브에는 내려받기 횟수 제한이 있어, 운영 환경에서는 필요한 이미지를 사내 레지스트리에 복제해 두기도 함
